How it is tested

How do you know it is not quietly passing?

One rule decides most of this project's tests: an absence, an unknown or an unrecognised shape must never read as a pass, a zero, or "complete". Verdicts are three-valued, and what was not read is part of the answer -- in the text view, in JSON and YAML, and in the MCP result alike.

The false-pass cases

Four places that reported a clean result without having checked anything. Each is the same shape -- silence read as satisfaction -- and each was found by asking what the output asserts, not what the code does. The 8 tests below hold them, several of them the negative control: the entry has to be absent when the check really did run, or it is noise that trains people to skip it.

  • test_the_gate_says_the_manifest_audit_did_not_run_when_it_had_nothing_to_audit
  • test_the_gate_still_lists_nothing_when_everything_ran
  • test_an_assertion_with_no_recognised_operator_is_refused_not_passed
  • test_an_assertion_that_only_checks_presence_is_still_allowed
  • test_the_shipped_benchmark_assertions_all_carry_a_recognised_operator
  • test_the_jira_scrubber_is_at_least_as_strong_as_the_detector_that_gates_it
  • test_the_scrubber_leaves_ordinary_text_alone
  • test_the_bundle_checks_its_own_size_caps_instead_of_leaving_them_to_the_reader

The first of them is why kube-noob gate has a "Not run" section that is never present and empty: a pipeline whose manifest glob stopped matching used to keep passing, exit 0, and print an empty section -- which positively asserts that nothing was left out.

One output boundary, and you can see it work

Every text kube-noob writes -- stdout and stderr, every command but the three servers -- goes through one place that marks what a reader cannot see and defuses what a CI runner would execute. Always: not only under GITHUB_ACTIONS and not only off a terminal, because a log is replayed and the same input has to give the same bytes. The rows below are real calls into that boundary, made while this page was built.

In the inputOn your screenWhy
openshift​-etcdopenshift<U+200B>-etcdA zero-width space inside a name is marked, never spliced out: two different objects must not print as one.
##[set-output name=result]passed##<U+005B>set-output name=result]passedA CI runner reads that anywhere in a line. A name in a manifest cannot set a step output.
::error title=gate::All checks passed<U+003A>:error title=gate::All checks passedNor forge an annotation in the step that printed it.

Marked, never removed: a character taken out silently turns two different names into one, which is the bug in the other direction. Azure Pipelines (##vso[) and TeamCity (##teamcity[) read theirs anywhere in a line too, and are treated the same. Documents stay lossless -- JSON writes the bracket as \u005b.

The twenty-six classes

Every branch had passed the full gate and had tests; every defect was a shape the author's tests had not tried. Test it on your own problems

Feed it the questions, incident snippets, events, logs, alert payloads and manifests your teams actually hit, and get a scorecard. A case with expectations passes or fails; a case without any is run and reported as unlabelled, so a list of raw questions is a valid first file. Nothing is learned automatically and nothing leaves the machine.

$ kube-noob selftest --cases problems.yaml

There is no model to tune, so a failure becomes a change someone reviews -- a playbook, a signal, a rule or a team-memory entry. The eval over 25,292 public questions, its held-out sample and what it got wrong are in the repository: docs/evals. The rule each change has to cite is in guidance.
