Privacy

kube-noob is open-source software that you run yourself: on your computer, in your CI, or in your cluster. The maintainers run no service for it and receive nothing from it. There are no accounts, no telemetry and no analytics. The website's contact and license forms are the one place the maintainer receives data: see The website.

There is no AI inside kube-noob. When you use it from Claude, OpenShift Lightspeed or another MCP client, that client and its model do the talking and call kube-noob's tools. What you share in that conversation is handled by that product under its own terms and privacy policy. kube-noob adds no network traffic of its own.

What it reads

  • Text you give it: manifests, events, logs, error messages and questions. It processes them in memory to answer; names it finds there (a pod, a Service, a label selector, a namespace) go only into the steps it prints.
  • Its bundled knowledge, and documents you index yourself with kube-noob corpus add-docs.
  • Only if you turn on cluster access: read-only requests to the Kubernetes or OpenShift API of your current kubeconfig context. It never reads Secrets and redacts values that look like credentials.

What it stores, on your machine only

Everything lives in the data directory: ~/.local/share/kube-noob by default, or KUBE_NOOB_DATA_DIR.

Nothing from a request is kept after it is answered, except the alert reports in the table above, which are kept from the Alertmanager payloads posted to them. What is listed above stays until you delete it; the maintainers never receive it.

kube-noob audit --receipt PATH and kube-noob gate --receipt PATH write the receipt to the path you name (owner-only, 0600), and it is written to be forwarded, so what it holds is deliberate and short: each input's path as you gave it and the absolute path it resolved to, the SHA-256 of each input's bytes and its size, the settings you passed, the resource references the audit already prints (Kind/namespace/name), the assumptions it already prints, and the verdict. Never the contents of any input, and never a finding's message. No hostname, no user name, no process id, no command line, and no environment: an unsigned document cannot attest to who produced it, so a self-asserted host in it would be a claim the document itself says it cannot support, and the fields are present and null with that reason in their place. An absolute path can name a person (/home/alex/work/...): that is the one identifying thing a receipt carries, it is there because a verifier has to find the file again, and it is removed by running the command with relative paths from the directory you want recorded. Nothing is sent anywhere, and kube-noob receipt verify reads only the receipt and the files the receipt names.

kube-noob must-gather analyze --report DIR writes report.md, report.json and, with --case-draft, case-draft.md to the folder you name; they hold redacted findings from the must-gather, never its Secrets, and nothing is sent anywhere. kube-noob bundle writes a redacted evidence pack to the folder you name (default ./kube-noob-bundle). The MCP server's log line records each tool name, argument sizes and duration, never argument contents.

What the redactor removes

One redactor (kube_noob.debug.cluster.redact_text) runs on what diagnose, insight, the must-gather report, build logs, the incident watch, the evidence bundle, cluster output and every alert report keep or show, and the learning-note filter refuses any text it would change. It replaces with *** (or a marker such as ***JWT***):

  • Authorization: Bearer <value>; a bare Bearer <value> of 16 characters or more with letters and digits; Authorization: Basic <value> when the value can be base64 credentials (8 characters or more of the base64 alphabets, with a digit or both cases), the whole value;
  • name=value, name: value and "name": "value" for password, passwd, pwd, secret, token, api_key (apikey, api-key) and access_key, also with up to four words in front: client_secret=, aws_secret_access_key=, DB_PASSWORD=, CLIENT_SECRET:, X-Auth-Token:. A reference to a Secret is left as written only where the text proves it is one: kubectl describe's <set to the key 'password' in secret 'orders-db'>, the same in words (secret 'orders-db' key 'password'), and a manifest's valueFrom/secretKeyRef. A value that merely looks like <name>/<key> (DB_PASSWORD: orders-db/password) is redacted, because password=prod-db/secret has the same shape and is a password: this over-redacts rather than leaks;
  • apikey <value> and access_key <value> when the value is 16 characters or more with letters and digits (so "rotate the apikey whenever a teammate leaves" stays as written);
  • secrets passed as flags: --password x, --db-password=x, --api-key x, --client-secret x, --token=x, --pwd x, --access-key x;
  • JWTs; AWS access key ids; Stripe-style sk_live_/rk_test_ keys of 24 characters or more; Vault, GitHub and Slack tokens; the password in scheme://user:password@host;
  • a private key from its -----BEGIN ... PRIVATE KEY----- line to its END line; a key cut short (no END after it) loses its base64 body -- lines separated by whitespace, by JSON-escaped \n, or by a newline and a log prefix (an RFC 3339 timestamp, a CRI stdout F, kubectl logs --prefix's [pod/name/container]), or the body flattened onto the BEGIN line -- and a BEGIN line with no body after it, which holds no key material, is left as written; the "private_key": "..." string of a service-account key file, also when it is cut short before its closing quote.

What it does not catch, so treat any text you hand kube-noob as possibly still holding these:

  • token <value> or password <value> with neither = nor : nor a leading dash: in prose a value and the next word look the same;
  • a password glued to a short flag, -p<password> (MySQL's form);
  • URL-encoded names, such as password%3D followed by the value;
  • a private key split across fields or quoted line by line (two labels, a JSON list of "..." lines), or whose lines carry a log prefix other than the three above;
  • a bare random string with no name and no known prefix, a Basic value under 8 characters or of one case without a digit, a bare Bearer value under 16 characters or without a digit, an apikey <value> under 16 characters or without a digit, and a JWT whose segments are under 8 characters.

What it sends, and where

By default, nothing. Each destination below is off until you turn it on.

The default web allowlist is kubernetes.io, helm.sh, docs.redhat.com, docs.openshift.com, access.redhat.com, cloud.redhat.com, developers.redhat.com, redhat.atlassian.net, docs.aws.amazon.com, github.com, raw.githubusercontent.com, stackrox.io, www.stackrox.io, gateway-api.sigs.k8s.io and kind.sigs.k8s.io, with their subdomains. kube-noob doctor prints what the running process can reach. Administrators can set offline: true (or KUBE_NOOB_OFFLINE=1) to block web access and downloads and to allow only local models; nothing later in the configuration can lift it.

The Claude plugin

The plugin starts the bundled server on your computer over stdio, with web access, cluster access and model calls off. Its Python dependencies are installed from PyPI at the versions and hashes in the plugin's uv.lock, into a throwaway environment in uv's cache (and uv's managed CPython once, if no Python 3.11 or later is installed). The plugin ships only the modules of the stdio server: no CLI, model agent, HTTP service, web client or cluster access, so it reads no credentials and makes no network calls of its own. Personal data is never requested. If text you paste contains some, it is processed in memory and not stored, except words you choose to put in a confirmed note or a learner id.

The directory plugin (kube-noob-skills)

kube-noob-skills contains Markdown and one image. There is no server in it, no Python and nothing of its own to run, and it downloads nothing. Its skills ask Claude to run the kube-noob CLI you installed, through Claude Code's Bash tool, under your own permission settings: you are asked before each command unless you have allowed such commands without asking. What happens is what the CLI does, held to this:

  • Engine. Only kube-noob already on your PATH. Not kubectl noob, which downloads kube-noob through uvx when kube-noob is missing, and no package launcher. If kube-noob is not installed the skill says so and gives the install command; installing is yours to do.
  • What is read. A private folder Claude makes for the session (umask 077 && mktemp -d), holding what you pasted, written with Claude's file-writing tool. Files you point Claude at: a chart folder (helm-audit, which runs your installed helm template with an empty Helm home), a rendered chart (helm template run by Claude with your approval), a Containerfile and its build context, a must-gather folder, SARIF files and a repository. kube-noob's own local stores, when a skill reads them: incidents (incidents list), the learning profile (learning show) and its configuration (config).
  • What is not reached. No command passes --cluster-enabled, --web-enabled, --live or --online, so kube-noob reads no cluster and makes no network connection.
  • What is written, and kept. Every command runs with KUBE_NOOB_LEARNING_ENABLED=false, so ordinary checks write nothing to kube-noob's data folder (without it, audit, diagnose, insight and policy explain add rule and playbook ids to learning.json there). The private folder is removed with rm -rf when the work is done. What stays is what you asked for: files written with -o (inside that folder unless you ask Claude to copy them out), learning progress when you read a lesson, submit an exercise or answer a quiz (exercise ids, scores and credits, in progress/ under the data folder), and a profile or an incident fix only when you ask to save one.
  • What Claude reads back. kube-noob's JSON for those files, with KUBE_NOOB_FOR_MODEL=1: text from your input that is shaped like instructions is neutralised before Claude reads it.

What you type goes to Claude as it always does. In chat on claude.ai the skills run nothing: they give you the command, and you choose what output to paste.

A remote MCP server pointing at your own kube-noob serve was considered for this plugin and is not shipped; see SECURITY.md.

The Agent Skill

The skill runs where Claude runs code: your computer in Claude Code, a sandbox for chat on claude.ai. It reads only the files named in a call, makes no network connections (web, cluster and model are forced off) and sends nothing to the maintainer. Like the server, it keeps learning progress and notes you confirm in kube-noob's data folder (KUBE_NOOB_DATA_DIR, else ~/.local/share/kube-noob) inside that environment; a claude.ai sandbox discards them when it ends.

The website (kube-noob.com)

A static site on GitHub Pages, built from this repository's releases. It sets no cookies, runs no analytics and loads its pages, scripts and fonts from its own host only. GitHub Pages, which serves it, keeps its own access logs under GitHub's privacy statement. Data leaves your browser in three cases, and only when you act:

  • Contact, feedback and student-license forms. When you submit one, what you typed goes to a Google Apps Script web app the maintainer runs, which stores it in the maintainer's private Google Sheet and emails the maintainer a copy. A message keeps its time, topic or area, rating, your name, email address, text and the page it was sent from. A student license keeps its id, your name, email address and school, and that you said you are a student; the license id is emailed to you. The data is used only to reply to you or to keep your student record, is not sold or shared, and is deleted on request through the contact form.
  • Bring your own AI. That page sends your Anthropic API key and your messages from your browser straight to api.anthropic.com, under Anthropic's terms for your key; the site never receives them. The key is kept in memory, or in the tab's session storage only if you tick the box.
  • Playground. It runs kube-noob's tools in your browser: what you paste stays on your device.
