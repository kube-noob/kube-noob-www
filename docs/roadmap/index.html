Roadmap: the ground truth for Kubernetes and OpenShift operations

Goal: a platform team deploys kube-noob once. Every developer and SRE then gets answers that are safe, cited and read-only first, about their own clusters, their own runbooks and their own past fixes, so the platform team's ticket queue shrinks. kube-noob has no AI inside: Claude, OpenShift Lightspeed or any MCP client does the talking, and the CLI works with no model at all. Updated 2026-11-03, after 0.7.1.

Principles

  • Models are the commodity layer. kube-noob competes on what a model cannot supply: the team's own confirmed fixes, deterministic checks, evidence in seconds, and what the network actually did.
  • The verifier never acts. Probes, server-side dry-runs, ticket writes and the gate are separate tiers, off by default, each action approved by a person.
  • Ship fetchers, not data. Red Hat Jira tickets, customer tickets and team memory stay where they were fetched; they are never bundled, published or exported to datasets.
  • Signals over prose. Alert names, event reasons, condition reasons and error templates are the join key between an error, a known issue and a past fix; text search is the fallback.
  • Land where AI is banned. Disconnected and regulated OpenShift first; every feature also works on ROSA, EKS, AKS, GKE and upstream Kubernetes.
  • A disclosure is not a decision. Every defect found in the 2026-11-03 review had one shape: the information was present and the decision ignored it. controlSummary was computed from a list the exception filter had already emptied; policy reach named ClusterNetworkPolicy under notEvaluated and returned allowed with exit 0; REMOVED_APIS answered "nothing removed" for versions nobody had read; compaction hoisted one finding list and left the other; policy_generate returned 95,000 tokens to a caller that cannot hold them; the weekly review left every superseded week open. In each case a careful human reading the whole output would have seen the caveat, and the gate, the pipeline or the model consuming it would not. So a caveat belongs in the verdict, the exit code or the shape -- the part that is acted on -- and a note beside it is at best a courtesy. When the two disagree, the note is the bug.

North star: time from an alert or a must-gather to an evidence pack, offline. Target: 60 seconds. Also tracked: memory hit rate and tickets answered without escalation.

The program

Reordered 2026-11-03 after four independent reviews. The order is: correctness before capability, capability before reach, reach before breadth. A verdict that can be wrong costs more than a feature that is missing.

The rule is therefore silent on the OpenShift family for an absent label, reports an explicit enforce: privileged on every platform, and on vanilla Kubernetes says the level is the cluster's AdmissionConfiguration default rather than claiming the namespace enforces nothing, because no manifest shows that default. KN-C016 (no ResourceQuota or LimitRange) is cross-object and declines to decide on a partial bundle, and it is LOW and advisory because a ClusterResourceQuota or a cluster default can supply either and no manifest in the namespace shows that. KN-S033 reports a paused MachineConfigPool, which upstream documents as stopping both the rendered config and the machine update, so OS, kubelet and runtime patches stop for every node in the pool. KN-S034 reports an OLM Subscription that upgrades without review, and the non-obvious half is that an ABSENT installPlanApproval means Automatic -- upstream's GetInstallPlanApproval returns Manual only when the field says Manual -- so omitting it chooses automatic upgrades rather than deferring the decision
N6 Decision chain in the terminal Shipped, and this row was stale. policy reach prints the deciding tier, the policy and the rule, why every other rule did not match, what was not evaluated and the NOT ENFORCED line for an inert tier; posture scan prints every attack-path step as from --edge--> to with its evidence underneath. Both were already in the terminal when this row still asked for them, which is its own small lesson: a roadmap row that nobody closes is as misleading as a count nobody updates
N7 Numeric targetPort with no declared containerPort Shipped as KN-V023 (LOW). KN-V012 owns the named case and is HIGH because the name must resolve or the Service gets no endpoints. The numeric case cannot be that, because containerPort is informational: a Service pointing at 8080 works whenever something listens there. So the rule fires only where the selected containers DO declare ports and the target is outside that set -- a typo rather than a style -- and says in the finding that it is not proof. A workload that declares no ports at all is silent, which is the absence-read-as-defect case this rule had to avoid. An omitted targetPort is checked too: it defaults to port, so treating its absence as safe would have been the same defect in the other direction (G208)
N8 API-server configuration from a must-gather TLS profile, audit policy and effective arguments from kubeapiservers.operator.openshift.io/cluster. Field stability across 4.x needs a real bundle first

A deviceClassName that names no DeviceClass in the bundle is deliberately NOT a rule. A DeviceClass is cluster-scoped and installed by the driver, so it is absent from almost every manifest set; flagging that absence would fire on every correct repository, which is the absence-read-as-defect failure rather than the absence-read-as-pass one. KN-ST001 can check an undeclared StorageClass only because KNOWN_STORAGE_CLASSES exists, and there is no comparable catalogue of device classes to build on -- a per-driver one is the only honest route and nobody has asked for it. N11 /metrics, a PrometheusRule, and an Alertmanager receiver route Shipped. /metrics on the same port behind the same bearer token (server.metrics.allowUnauthenticated opens it for a mesh that authenticates upstream), instrumented at run_tool, the one point both the MCP tools and the REST routes pass through, so the two surfaces cannot drift apart. No new dependency: the exposition format is four fields per line. The design decisions are the content. Every label value comes from a fixed set, because run_tool labels an anticipated failure with the exception's class name and exception types are open-ended -- a caller who can provoke a new one would otherwise add a Prometheus label value each time, which is a cardinality attack on the monitoring system rather than on this process. Knowledge age and corpus date are kept as two separate metrics: the first is the IMAGE's review date, fixed at build time, and the second exists only where a corpus is imported, so conflating them would alert about a refresh job most installs do not run. The error-ratio alert counts crash and error and deliberately not invalid-arguments: a caller sending bad input is not this pod failing. And the third part of R6.5 finally has somewhere to post: POST /v1/alerts takes an Alertmanager payload in its own shape, which needed a route that passes the body as one argument rather than as an argument map (G236)
N12 Gate findings as pull-request annotations Shipped. gate --github-annotations, on by default in the action. It took more than the four lines this row estimated, and GitHub's cap is why: it shows ten annotations of each kind per step and drops the eleventh silently, so nine are annotated and the tenth says how many are not shown (G215)
N13 Caller identity in audit records, and reading as the caller Ranked first by the FedRAMP High requirements and by every multi-tenant reviewer: today authorization is one shared bearer token and the server logs the tool, argument sizes, outcome and duration but never who asked. It stays an enterprise candidate in editions.md rather than a 0.9.0 promise, because the honest version needs the OAuth proxy wired to a real identity provider and a cluster to prove it on -- but it is recorded here so the ranking is visible rather than implied

From the external reviews, 2026-11-06

Three external AI reviews proposed about 250 checks. Five survived, and ideation-review.md records all of them with the verdict and the reason, so the refusals are findable instead of remembered. The test each had to pass: a real gap, decidable from evidence this tool can already reach, and not a new engine, integration or credential.

# Item Why it survived
R1 ~~Excessive RBAC access to Secret objects, as a rule~~ Withdrawn, and replaced by a correction. The item rested on "no catalogue rule reports it on its own", which was false: KN-S017 has always had a Secret-read branch. Reading the reviews' gap lists rather than the code produced a backlog item for work that existed. What the reviews really asked for was the distinction the rule was NOT making -- list returns the Secrets' contents, a get returns the ones whose names you know -- and that shipped as G240, with a false positive the rule turned out to have: a get narrowed by resourceNames is the pattern upstream recommends and was being reported as an escalation path
R2 Certificate expiry from TLS Secrets and Routes in the bundle Blocked on a decision the maintainer owns: a new runtime dependency. All three reviews asked for it and nothing reads a notAfter today, so the gap is real. Reading one needs an X.509 parser. cryptography is already in requirements.lock, but transitively, and building a rule on a dependency this project does not declare is precisely G228 -- it works until the graph moves. Declaring it directly is the honest version, and it is not a small thing in a tool whose argument is that it installs hash-locked into a disconnected cluster and ships a vendored plugin server with its own lock. The alternative is an ASN.1 walk of the DER by hand, where a wrong verdict about a certificate is worse than no verdict. Neither choice should be made silently by an agent at 9am, so it is written down instead
R3 Registry and publisher allowlist Shipped as KN-S036 (G241). The allowlist is audit.allowedRegistries in the configuration file, not a command-line flag or a tool argument, because which registries an organisation approved is an organisational decision that should be the same for every caller of a deployment. With none configured the rule declines rather than passing every image. The part worth knowing is the reference parser: Docker's rule is that the first path component is the registry only when it looks like a host, so nginx and bitnami/nginx both come from docker.io however little they look like it, and an allowlist that missed that would pass every unqualified image. An entry may narrow to one organisation (quay.io/my-org), which matters for a registry anyone can push to
R3b ~~Generate the admission policy for KN-S036~~ Shipped (G242). policy generate reads audit.allowedRegistries and emits the policy for both engines; the CEL is prefix matching with its separators and agrees with the audit on 80 reference shapes and on the random corpus. Two kinds of allowlist are refused rather than compiled, with the reason in the header: one naming docker.io, which needs string surgery the API server's CEL cannot do, and one whose host has no dot, port or localhost, where myregistry/app comes from Docker Hub and the policy would admit what the audit reports. An empty list still generates nothing
R3c ~~The admission webhook evaluates KN-S036 too~~ Shipped (G243). The webhook's Config carries the allowlist, the chart writes it into both config files so the audit, the webhook and policy generate give one verdict, and the webhook restarts when it changes. Enforcing the rule without a list is refused at install and at startup rather than denying nothing, and an entry that could never match an image (MyRegistry, myregistry) is refused by the values schema and when the configuration loads
R4 ~~A detection-coverage statement for the logging family~~ Shipped (G244, corrected by G249 and G252). From the same APIServer object KN-S035 reads, kube_noob.audit.detection states which categories of API activity the cluster's settings can record and which they cannot, per group where a customRules entry overrides the top level. Every row is read from the policy manifests cluster-kube-apiserver-operator generates the real policy from, not from the API type's summary comment, which is stale on Events -- dropped through 4.17 standalone, through 4.18 on a hosted control plane, because HyperShift vendors its own copy of that generator. Two rows are therefore decided by --platform and --version together and reported as undecidable without them; a Kubernetes version is mapped rather than compared; and an unknown profile, a malformed spec.audit, a non-mapping metadata and a bundle with two singletons are all undecidable rather than guessed. It appears in kube-noob audit and the audit_manifests tool, only on OpenShift and only when the bundle carries the object
R6 Admission sees the pod specs inside operator CRDs -- webhook done, policies left Half shipped (G248): the bundled webhook runs the audit, so it could always find a privileged container in a KServe predictor or a Ray head; the chart simply never asked the API server to send those resources, and now it does for serving.kserve.io and ray.io, with the list asserted against the audit's own table of pod-spec-carrying kinds. What is left is the generated ValidatingAdmissionPolicies and Kyverno policies: each kind's pod spec sits at a different path, a worker-group list needs an all over it, and a variable that indexes a path the object does not have fails the policy closed -- under failurePolicy: Fail a wrong guess denies every InferenceService in the cluster. It needs the kind-cluster job with CRD stand-ins (scripts/policy_kind_crds.yaml already carries six), not a local test, and the generated file states the gap until then
R7 ~~kubectl debug goes through a subresource nothing matches~~ Shipped for the webhook (G250), and closed for the policies with a reason rather than a change. The webhook evaluates pods/ephemeralcontainers and no other subresource: the owner check does not apply there (no owner carries an ephemeral container) and only the findings the request ADDS are reported, so a Pod that already breaks an enforced rule can still be debugged. The generated policies are deliberately not extended to it: a ValidatingAdmissionPolicy has no before-and-after comparison, so one matching the subresource would refuse every debug of an already-failing Pod -- a trap rather than a control
R5 Operator and add-on vulnerability surface Reachable once E2's operator inventory exists, by matching installed ClusterServiceVersion versions against the known-issue corpus already shipped. Gated on E2, recorded so it is not rediscovered

The surfaces: what is code and what a person actually looks at

Measured 2026-11-06, not estimated, and generated by scripts/doc_numbers.py rather than typed. The engine is about 64,000 lines across 150 modules with about 44,000 lines of tests (both to the nearest thousand, because a line count that changes with every commit is not a claim worth gating on), and exactly 93 rules, 48 MCP tools, 108 commands and 14 chart templates. The part a human looks at is three things, and only one of them is in this repository:

Surface State Who renders it
The terminal The real interface. Every command has a text view, and the text view is where the caveats live — not checked:, assumed:, not evaluated:, the shows/does-not-show pair kube-noob
An assistant The MCP tools and the skill. There is no layout to design: the JSON is the interface, which is why a caveat that lives only in the text renderer is a defect and not a cosmetic gap (G221) Claude, or any MCP client
Borrowed UI SARIF into GitHub code scanning, the job summary, pull-request annotations (G215), OSCAL for an assessor's own tooling GitHub, or the assessor's tool
The website A separate repository that cannot be edited from a session attached to this one. website-updates.md is the queue; it currently holds 10 rows and does not know the date of the last site update the owner

There is no graphical interface and no server: --format is text, json or yaml, and the one thing the product renders is a single self-contained HTML file a reviewer opens from an attachment. That is a deliberate position for a tool that runs offline in someone else's cluster. The three items it left are UI work rather than engine work:

# Item Why, and what would be true when it is done
U1 A self-contained HTML report for posture report and gate The audience for per-control standing and the KSI crosswalk is a compliance reviewer, and what they get today is terminal text or JSON. One file, no network, no JavaScript dependency, openable from an email attachment, carrying the same caveats the text view carries — including audited: false, notCheckedBeyond and the shows/does-not-show pair, because an HTML report that drops them is the G221 defect in a third format. Testable the way the videos are: render it, parse it, assert the caveats are present
U4 ~~A posture report carries the audit's own assumptions~~ Shipped (G255). Found while building U3, and the same defect in a fifth place. drift.snapshot runs the audit and keeps its findings and its coverage record, and drops report.assumptions -- which is where "N pod spec(s) are in kinds kube-noob has no reader for, NOT audited" (G232) is written. So a folder of snapshots of Argo Rollouts reports every day as a complete read, on the page a reviewer opens, while a whole class of workload was never looked at. The snapshot should keep them, the report should carry them forward, and the HTML page already renders assumptions as a caveat the moment they are there. The completeness column says what it covers in the meantime
U5 ~~The report reads as a document of record, not a dump of tables~~ Shipped (G257). The HTML report is the only thing that leaves the terminal: a reviewer, an auditor or a manager opens it, often prints it into an audit package, and today has to assemble the answer themselves from about 7 000 pixels of h2 + table with no verdict, no contents and no anchors. Designed, not yet built: a masthead carrying the verdict as a sentence, the three numbers that decide the next action (open findings, not-evaluated-or-withheld, evaluated-and-clean) and a provenance strip; limits of this examination as section 1, numbered and in the document's own voice rather than a yellow strip a reader is trained to skim; findings and control rows each with an id so a reviewer can link a colleague to one line; controls ranked by consequence with the silent ones behind a <details> the print stylesheet forces open; and real print rules -- @page, a repeating thead, no break inside a row, a running identity on every sheet. Structure goes blue so red belongs to findings alone. The constraint that shapes all of it is unchanged: one file, system fonts, no script and nothing fetched. U4 had to land first, or section 1 cannot list the kinds that were never read
P10 Host-networked pods are selected by policies that cannot select them Found red-teaming P4, and inherited rather than introduced by it. The v1alpha2 spec says plainly that host-networked pods are not included in subject selection, nor by the namespaces and pods peers; anp.subject_matches and anp.peer_matches, which both evaluators share, never look at host_network. So an Admin-tier Accept whose subject is a namespace selector turns shop/daemonset/agent -- a hostNetwork pod -- from the honest undetermined it gets with no policy present into allowed, on the strength of a policy that cannot select it. Not fixed with P4 because the primitives are shared: changing them changes v1alpha1 verdicts too, and that wants its own pass with its own tests rather than a late edit. The same pass should finish the MaxItems: 25 enforcement, which covers rules and peers but not protocols or networks
U2 A Grafana dashboard JSON beside N11's /metrics Shipped as deploy/grafana/kube-noob.json: version and uptime, calls per second by outcome, the failure ratio drawn with the same expression the PrometheusRule alerts on, which tools are used, and the duration percentiles. A datasource variable rather than a hard-coded uid, every panel scoped to a chosen $job, and the rule that kept this item closed is now a test -- every metric any panel queries must be one the renderer emits, because a panel pointing at a metric that does not exist shows "No data" for ever and nobody can tell that from a quiet system (G239)
U3 ~~Charts in the HTML report~~ Shipped (G254). Inline SVG drawn from counts the page already states: findings by severity on a gate report, open findings per control and the five standing buckets as a stacked bar on a posture report, and open against excepted findings across the snapshots posture report still keeps. No script, no stylesheet, no font, no library, nothing fetched -- the constraint that makes the page forwardable is the one that decided how the charts are drawn. Three rules hold it: a chart may show only what a table on the same page shows, every bar is labelled with its name and its count so colour carries nothing on its own, and a count that was withheld is not drawn -- the trend is withheld entirely when any snapshot in the series could not read every resource, because a line through a floor publishes a fall in findings that may only be a fall in what kube-noob was allowed to see. The palettes were run through a colour-vision validator in both light and dark rather than eyeballed

Deliberately not on this list: a web application, a hosted console, an authentication interface, anything with a server-side session. There is no legal entity behind this project (editions.md), so there is nothing to host it on and nobody to be accountable for the data it would hold.

What this refuses to be

The long-form version, proposal by proposal, is in ideation-review.md: about 250 externally proposed checks, five taken, the rest refused with the reason grouped so the argument is visible rather than the verdict alone.

Encompassing more means reading more artifacts, emitting more formats and reaching more places. It does not mean taking privileges the tool has promised not to take, and it does not mean competing on rule count.

Refused Why
A node agent, DaemonSet, or any nodes/proxy or exec read Breaks the contract every other surface rests on. The Compliance Operator path gives the same evidence read-only
Embedding CIS Benchmark text, or claiming "CIS compliance" The benchmarks are non-commercial-use and not redistributable. Section numbers reach us free through ComplianceAsCode and the Compliance Operator's own annotations
A single compliance score, or a percentage of 800-53 28 of about 1,189 controls. A percentage invites exactly the misreading FedRAMP warns against
Image registry scanning Network, and Trivy and RHACS own it. Keep ingesting their output
Hosted compute, hosted cluster state, or shareable server-side links "Nothing leaves your device" is the product. The browser playground already delivers zero-install without a backend
Any model inside the tool The positioning, and a test enforces it
ISO 27001 mapping, certificate expiry from Secrets, a generic RBAC viewer No free machine-readable crosswalk; forbidden; already answered by attack paths

The honest ceiling on compliance

kube-noob names 30 of NIST SP 800-53 Rev. 5's controls across its 93 rules. The right sentence is "machine-readable evidence bearing on these 30 controls, from these object kinds, over this scope, with these rules not applicable and these inputs unreadable" — never "compliance coverage", never a percentage. It does not assess the other controls, it does not scan nodes itself, and it is not a substitute for a continuous posture platform. A GRC team will not switch to it; they will run it beside what they already have, for the evidence those tools cannot export from a disconnected cluster.

Riskiest assumptions and the cheapest test

Assumption Cheapest test State
Team memory gets reused often enough to matter kube-noob memory replay on one team's last 50 resolved tickets and the 4 weeks after: at least 30% useful matches Blocked on a design partner, not on code. The harness, the gate and the no-hindsight controls exist; "useful" is a human label, so it needs one team's export and a grader
Platform teams will let an OSS tool server into the cluster Show doctor, PRIVACY.md and SECURITY.md to two OpenShift admins; ask what blocks approval Not run
Developers will ask it before opening a ticket Turn on the Lightspeed integration for one team; compare ticket counts for the top 5 categories over 4 weeks Not run

The first row is the one that decides whether the ledger is a moat or a feature. Until that number exists and is written down as pass or fail, kube-noob is a careful linter with two answers no other tool gives.
