Security Policy

Reporting a vulnerability

Please report vulnerabilities privately through GitHub's "Report a vulnerability" button on the repository's Security tab (private vulnerability reporting). Do not open a public issue. Expect an acknowledgement within 3 business days and a fix or mitigation plan within 30 days for confirmed issues.

Supported versions

The latest minor release receives security fixes.

Default posture

kube-noob makes no outbound connections and touches no cluster unless you enable it. This is tested in CI and was verified end to end inside a network namespace with no route (docs/release-readiness.md). With web access enabled it only performs HTTPS GETs to allowlisted documentation domains, refuses non-text content types (archives, binaries, scripts), streams at most web.maxBytes, never writes the content to disk and never executes it. The admin lock (offline: true / KUBE_NOOB_OFFLINE=1) overrides webEnabled, blocks corpus downloads and allows only loopback or in-cluster model endpoints; no later configuration source can lift it. kube-noob doctor reports the effective posture. The local learning file stores only user-confirmed summaries and ids, never logs, manifests or credentials. With alertReports.store the HTTP server keeps an evidence report for each Alertmanager payload posted to POST /v1/alert-reports in its own data directory (owner-only, bounded by count, age and size, never written through a link), built from the payload and local knowledge alone: the receiver reads no cluster, fetches nothing and runs nothing a payload names, and one post gets alertReports.budgetSeconds (30) of work at most, counted from receipt, off the event loop; at most two reports are built at once by the receiver and the MCP tool together, a report slot is taken only once the body has been read and is held only while the report is built, and a post that waits more than 5 s for a slot is answered 503 with Retry-After. Every request body must arrive within 10 s (else 408), so a sender that trickles holds neither a slot nor memory for long. The MCP server's only subprocesses are read-only oc/kubectl calls (argv, no shell) when cluster access is enabled; the maintainer CLI commands corpus build --online and helm-audit run git and helm template locally.

The Agent Skill (skill/kube-noob) cannot be configured out of this posture: its runner forces the offline lock, web and cluster off and no model on every call, ignoring the config file and KUBE_NOOB_* variables, imports the bundled server source only (it refuses another installed kube-noob), and its tools start no other program and open no connection (a test runs them with both refused).

Security design

Area Control
Network webEnabled: false by default; all outbound HTTP goes through one guarded client; web requests (and every redirect) must be HTTPS to an allowlisted domain.
Cluster access Opt-in (cluster.enabled), read-only verbs on an allowlist of resources, Secrets never readable, ConfigMap values / sensitive env values / token-like log content redacted, strict argument validation, no shell. A read that failed is never taken for "nothing there" (G279): absence is recognised only in the backend's own words, and a list answer must name its kind, its items and their namespace and be complete. Known limitation: on the in-cluster backend a resource counts as not served when the answer is a 404 whose body is exactly 404 page not found, the API server's own text, but Go reverse proxies (Traefik, kube-rbac-proxy) send the same body, so a proxy in front of the API server that does not route a group reads as that group not being served.
HTTP server Refuses to bind non-loopback without a bearer token (constant-time compare, and two Authorization headers are refused rather than resolved last-wins) unless explicitly overridden; DNS-rebinding protection with a Host allowlist; health endpoints are the only unauthenticated paths. The body limit is 1.5 MiB, below the 1,000,000-character argument cap so no valid request is refused, and a body on the public health paths is refused with 405 before it is buffered, so an unauthenticated caller cannot make the server hold memory. The REST routes (/v1/...) are behind the same token and body limit, pass the same Host and Origin checks, accept only application/json posts, and exist only for the tools the shared server offers (none that writes). /metrics is inside the same token check unless server.metrics.allowUnauthenticated opens it, answers GET and HEAD only, and carries counters whose every label value comes from a fixed set -- an exception type a caller can provoke collapses to error rather than becoming a new Prometheus label.
Input parsing YAML SafeLoader only, 5 MB / 1000-document caps, alias-expansion budget against billion-laughs.
Suggested commands Steps a diagnosis prints are read-only and copy-paste safe: a name taken from the input (pod, Service, label selector, namespace) is pasted into a command only when it is made of letters, digits and @._:/=+#%,- and does not start with #, otherwise its placeholder stays; a Service selector is used only when every key and value is a valid label; no step prints a Secret's values. Every validator ends with \Z, not $ (Python's $ also matches before a final newline, so a must-gather namespace "shop\n" once split a printed step into two shell lines); a test fails on any new validator anchored with $.
Must-gathers Opened as a stream or a walk with no links followed; nothing extracted or run; Secrets-named files never read; YAML pre-scanned for aliases, documents and depth before libyaml loads it. The analyze_must_gather MCP tool is offered by the HTTP server only with mustGather.allowedDir and reads only paths that resolve inside it (links resolved first); it is not in the Claude plugin.
Prompt injection Every MCP tool result and the knowledge resource is cleaned before it leaves the server. Removed: invisible Unicode (tags, bidi overrides, zero-width characters other than a ZWJ or ZWNJ after non-ASCII text, where emoji and scripts such as Persian and Devanagari need them, soft hyphens and other word splitters), chat-template and role markers, tool-call markup, instructions aimed at a model (matched on a normalised copy: full-width and mathematical letters folded, Cyrillic and Greek look-alikes mapped, entities and colour codes decoded, hyphenated line breaks joined; English, Spanish, French, German, Italian, Portuguese, Russian, Chinese, Japanese, Korean; inside base64), every remote image address and a link's query when it can carry data. Flagged but kept: phrases that are operations as often as attacks ("send the credentials to vault.example.com"). The result carries untrusted: true and the signals. Evals: 66 of 66 and 25 of 25 with no finding on 148 benign lines; the red team's 50 new attacks 48 caught and its 55 adversarial benign lines 1 altered (a remote badge image), 8 flagged; these sets were used to tune, RT2 measures blind. Terminal and file output is cleaned too (G279): every CLI TEXT write to stdout or stderr -- the text view, --compact, errors -- passes through sanitize.visible_lines at one boundary, and the HTML report and the Markdown writers use the same helper; MCP text content goes through the same rule (clean and visible are one implementation), so a name in a structured result reads openshift<U+200B>-etcd; the injection matcher reads past markers as it reads past the characters. Terminal escape sequences (CSI, OSC 8 links, OSC 52 clipboard writes) are removed; other control characters, line and paragraph separators, private-use characters, noncharacters and the Braille blank become a space; format and default-ignorable characters (bidi overrides and marks, tag characters, soft hyphen, BOM, zero-width spaces, Hangul fillers, CGJ, Mongolian and stray variation selectors) are removed, and shown as <U+XXXX> when they sit between two identifier characters, so web<U+3164>x is not read as webx; combining marks are capped at four in a row; ZWJ and ZWNJ are kept after non-ASCII text, where scripts and emoji need them. Documents are not cleaned but escaped by their encoder, losslessly: JSON by json.dumps, YAML by a dumper that double-quotes and escapes any string that would not print, so what is printed equals what -o writes and loads back to the same data. The servers serve, mcp and admission serve are not wrapped: their stdout is a protocol stream or a server log built from messages made safe where they are built. watch prints text views and is wrapped. An escape sequence between two identifier characters is shown as <ESC> (web<ESC>x is not webx, api<ESC>.internal is not api.internal) and removed in prose. No caller can remove a character from inside a name without a trace: marking is the default of every variant, the MCP cleaner included, and a caller that asks for no markers gets a space there, never nothing; a test runs every call site in src with its own arguments (fourth review). A document written to a closed pipe exits 141, like text: each document writer flushes inside the command, where the error is caught. An error kube-noob did not anticipate is one cleaned line on stderr with exit 4; KUBE_NOOB_DEBUG=1 adds the traceback, through the same boundary.
CI logs A GitHub Actions runner reads a workflow command from every line a step writes: ::name:: at the start of a line and the legacy ##[name] anywhere in it (actions/runner v2.321.0 ActionCommand.TryParseV2 / TryParse); Azure Pipelines reads ##vso[ and TeamCity ##teamcity[ anywhere in a line. Every text kube-noob writes, stdout and stderr, every command but the three servers, goes through sanitize.CommandGuard at the output boundary, always -- not only under GITHUB_ACTIONS and not only off a terminal, because a log is replayed and the same input must give the same bytes: the bracket of ##[, ##vso[ or ##teamcity[ (one rule: ##, letters, [) is shown as <U+005B> and the first colon of a line-leading :: as <U+003A>, the marker style visible uses, so the change is visible and cannot be mistaken for text. Comment and header lines kube-noob composes into a document (the policy generate header, which echoes the exceptions file) get the same treatment; Markdown reports too. Documents stay lossless: JSON writes the bracket as \u005b; YAML double-quotes on one line, with \x5B, only a string that holds such a prefix or a :: a line could start with (listen [::]:80;, fe80::1 and std::io keep their style); the SARIF, Code Quality and HTML files gate writes, the AdmissionReview admission review prints, the debug bundle and the chart files are escaped the same way. The only commands kube-noob emits are the annotations gate --github-annotations builds: their text is cleaned, then escaped per the toolkit's rules, with service messages broken. tests/test_workflow_commands.py ports the runner's two parsers; it and tests/test_g279_third_review.py find no other command in any output (G279).
HTML report One file with nothing the browser fetches and nothing it runs: no script, stylesheet, font or image, and the charts are inline SVG rather than a plotting library. Every value from a manifest is escaped before it is written, inside the SVG as well as in the page, because a <title> or a label is as good a place to run a script as a table cell is; a test parses what is produced and fails on any src, <link href>, inline handler, <script>, <use>, <image> or <foreignObject>.
Pre-action hook kube-noob hook claude-code (and the plugin's hook, off until its verify_cluster_commands option is on) runs kube-noob verify before a Bash command that changes cluster state: an allow passes, a deny is blocked with exit 2, a not-determined asks the user with the reasons (PreToolUse ask; in a -p run nobody can answer, so Claude Code denies it), and the hook's own errors and an exhausted 20-second budget block -- the check runs in a child process that is killed at the budget, because a thread cannot stop a regular expression running in C (a Makefile line built for it held the old hook 62 seconds, past Claude Code's timeout). It reads the command as data and never runs it; it reads files only inside the working directory the hook input names, follows no link (a chart with a link in it is not rendered), fetches nothing, and runs only a helm found in an absolute PATH entry outside the project tree (its git root; a tree that is $HOME or / excludes nothing). A file an earlier command on the same line may have written (cp, sed -i, cat >, git checkout, any program it does not know) makes the verdict not determined; command substitutions are followed in ${...}, $((...)) and unquoted here-documents; cd is followed to read the script the shell will run. A program the reader does not model is opaque, not transparent: a kube command in its arguments (aws-vault exec prod -- kubectl delete ..., npx kubectl ..., nix-shell --run '...') or text naming a kube tool on its standard input (echo '...' | at now, ssh host < cmds.txt, make -f -) makes the line not determined whatever the program is called; one that names no kube command passes. make is read through -f, -C, include, $(shell ...), inline and continued recipes, and a kube tool in a command-line variable or --eval is not determined; npm, pnpm, yarn and bun scripts are read in the package --prefix, -C, --dir, --cwd or -w names, and npm exec, npx, pnpm dlx, yarn dlx and bunx are opaque programs. Every name, path, command and message from the repository in its messages is quoted between « », one printable line, capped; text shaped like an instruction is flagged. A kubectl command line is read the way cobra reads it (cobra v1.10.2 command.go stripFlags): before the subcommand an unknown flag takes the next word as its value, so kubectl -o yaml delete ns prod is a delete; a root flag kubectl does not define, a -- before the subcommand, and a subcommand only known at run time ($SUB, $(...), a glob or a brace) are not determined. sudo -s/-i/--shell/--login and doas -s run the rest as a shell command line; xargs and GNU parallel are read with their input (-a FILE, ::::, here-strings, pipes from echo, cat, tee or base64 -d); project runners are read where their file can be (justfile, Taskfile, deno.json) and otherwise not determined when it names a kube tool (tox.ini, noxfile.py, Earthfile, compose files, .pre-commit-config.yaml); go run, cargo run, bazel run and a script that starts other programs are not determined; git's program-running options (bisect run, rebase -x, --upload-pack, config alias, --ext-diff) are read; cluster lifecycle tools (kind, minikube, k3d, kops, talosctl, clusterctl, openshift-install, crc, microk8s) and the cluster operations of gcloud, aws, az and doctl ask unless they only read or update the local kubeconfig. Where it fails open: Claude Code lets a tool call through when a hook cannot start, exits with a code other than 0 or 2, or outlives its timeout, unless the entry sets "onFailure": "block" (Claude Code v2.1.295 or later; older versions ignore it). The entry hook install writes -- only for a user who asked for it -- sets it, so there a missing kube-noob, a crash or a timeout blocks. The plugin's entry, which every plugin user gets, does not set it; instead its command is a POSIX sh guard that reads the opt-in from CLAUDE_PLUGIN_OPTION_VERIFY_CLUSTER_COMMANDS (the variable Claude Code exports to plugin hooks; exact match, ASCII case ignored, nothing stripped, the same rule as the Python side). Off, it exits 0 without starting any program. On, it blocks by itself with exit 2 and one line on stderr when uv cannot be found or its run exits with anything but 0 or 2, and passes the bundled hook's answer through otherwise -- on any Claude Code version. The guard also kills a uv run that has not finished in 45 seconds and blocks (exit 2), so a uv stalled resolving on a slow network does not reach Claude Code's 60-second timeout, which would let the call through. What remains open for a plugin user who turned the check on: a system with no sleep program, where the 45-second watchdog cannot run; and Windows without Git Bash, where Claude Code runs a shell-form hook in PowerShell, the guard does not parse, and the error is non-blocking -- the check simply does not run, for anyone. A Windows user who wants the check uses Git Bash (or CLAUDE_CODE_GIT_BASH_PATH) or kube-noob hook install. The PowerShell case has not been run. What it does not stop: it is a check in the agent's own harness, not a security boundary. An agent with a shell can bypass any client-side hook: Python, Node or another language building a command at run time ("kube"+"ctl"), the Kubernetes API with curl and a token, a kubectl copied or linked under another name, a compiled program, a Makefile target built from make variables, a dependency's install script, an environment variable exported by an earlier call (KUBECTL_EXTERNAL_DIFF, PATH), a kubectl placed in a virtualenv's bin, editing the settings that install the hook, or another tool or session. It does not judge what a day-2 change does to the running cluster. Allowed by design, because none can add a finding to a manifest: rollout restart|pause|resume, scale and autoscale of one named object; label or annotate of one object that is not a namespace or node, with no Pod Security, SCC, node-selector or cloud-identity key; deleting pods by name; create namespace|configmap|secret|serviceaccount from literals or from files in the tree; oc new-project; expose as a ClusterIP Service without --external-ip; set env without a credential, a URL with a password in it or a variable that loads code (LD_PRELOAD, NODE_OPTIONS, JAVA_TOOL_OPTIONS ...); a patch by name that touches only replicas, pauses, timings, labels or annotations; kubectx, kubens, oc project and config set-context --current --namespace; port-forward and proxy on loopback (they open a local port and store nothing; a non-loopback --address, a widened --accept-hosts or --disable-filter asks); a dry run (--dry-run=client|server) on any verb that defines the flag, since nothing persists -- with a note when a real run of the manifest would be denied; --help on a verb the tool itself defines (on a plugin word the plugin runs, so that asks); oc adm node-logs, must-gather with the default image, release info and the upgrade status, status and recommend; krew list|info|search, neat and helm diff; and a day-2 change with an explicit --context, --cluster, --kubeconfig or KUBECONFIG=, which is judged the same as without one (a manifest sent to an explicit cluster asks). The full table, run by a test, is in docs/use-cases.md. A command longer than the reader's 20,000 characters is allowed only when it is one inert echo, printf or here-document naming no kube tool; anything else past the cap asks. Each of these asks instead: a --dry-run that is the value of the bare flag before it (-n --dry-run=client runs for real) or followed by a run-time word (the last one wins); delete pod NAME --raw URI (the URI is deleted, the name ignored) or with -f or a second kind; a day-2 change with --as, --token, --server, --user, --username/--password, client-certificate or CA flags (who it runs as or where the credential goes); a scale, restart, pod delete, label, patch or set env in kube-system, kube-public, kube-node-lease or openshift-*, or of etcd, kube-apiserver or cluster-version-operator; a day-2 word only known at run time; helm's --post-renderer and kustomize's --enable-* on any verb (a program on this machine); oc adm prune and every other oc adm outside the read list; create secret docker-registry; set env of PATH, a proxy or a CA-bundle variable; expose --type that is not a literal ClusterIP; a proxy with --accept-paths, --reject-paths or --reject-methods; oc adm must-gather --image. The printed reason never carries a credential's value (--token V, -p V, -pV, --kube-token V, --env PASSWORD=V, ://user:pw@), and a hidden character in a command is shown as <U+200B>, the same under every terminal encoding. PowerShell: a command that names a kube tool, or that builds or runs a command its text does not spell (&, iex, Invoke-Expression, gcm, a .ps1, wsl, cmd /c, string concatenation, base64), asks; verify still does not read PowerShell. a cloud-identity key on a service account (eks.amazonaws.com/role-arn, iam.gke.io/gcp-service-account, azure.workload.identity/*), --external-ip (CVE-2020-8554), oc expose svc (a Route), --from-file/--from-env-file outside the tree (it copies a file from this machine into the cluster), a code-loading variable in set env, helm plugin install, and fc -s/r (they re-run a command from the shell's history). It does not judge a PersistentVolume's hostPath (no audit rule reads it), or a namespace's Pod Security level below --fail-on (KN-S032 is medium). It checks changes, not reads: printing or sending away what the cluster holds (kubectl get secrets -A -o yaml | curl ..., config view --raw, oc whoami -t) is out of scope, as is what a container image or docker build does without cluster credentials, and what go test runs. Other deployers -- helmfile, argocd, flux, skaffold, terraform, tofu, pulumi, istioctl, velero, kubeadm, kpt, crossplane, eksctl, ansible-playbook -- are not modelled: their reading subcommands pass and the rest ask; kapp deploy -f FILE is checked like kubectl apply. PowerShell commands are not parsed: one that names a kube tool asks. The server-side control is the admission webhook with admission.enforce, and the cluster's own RBAC. KUBE_NOOB_HOOK=off in the environment Claude Code starts with turns the hook off for the human; KUBE_NOOB_HOOK=off kubectl ... in a command does not.

Claude plugin Runs the readable stdio server bundled in the plugin with uv run --frozen --isolated; every dependency is pinned by version and sha256 in uv.lock; no LLM SDK is installed and no package-manager variable is set; only the modules the stdio server imports ship, so nothing in the plugin reads a credential; web, cluster and model calls are off.
Directory plugin kube-noob-skills ships Markdown and JSON only: no server, script, hook or bin/, and it downloads nothing. Its skills run the CLI the user installed (kube-noob on the PATH, never kubectl noob or a package launcher, both of which can fetch it) through Claude's Bash tool, under the user's own permission settings; the plugin pre-approves no tool and runs nothing as a skill loads. Pasted text is written into a private per-session folder (umask 077, mktemp -d) with Claude's file-writing tool, never a heredoc, and the folder is removed after. Every command runs with KUBE_NOOB_FOR_MODEL=1, so text from the input shaped like instructions is neutralised by kube_noob.sanitize and flagged before Claude reads it, and with KUBE_NOOB_LEARNING_ENABLED=false; output goes to a file with the exit code printed, and only exit 0 or 1 with a complete JSON document counts as a result. No command it runs carries --cluster-enabled, --web-enabled, --live or --online. Tests parse every command line against the real argument parser, and run every command a skill names on a fixture to check the fields its table cites.
Availability A burst of idle or slow connections starves the HTTP server's connection pool: uvicorn counts connections towards limit_concurrency and nothing reclaims one that never sent a request (timeout_keep_alive applies between requests on a keep-alive connection), so every request including the kubelet's probes answers 503 until they close. kube-noob cannot close this in process. Buffered-body memory is bounded -- the limit is 1.5 MiB, a body must arrive within 10 s, and at most eight bodies over 256 KiB wait in memory for their tool (or, for an alert report, for a report slot) at once; one more waits for room until its read deadline and is then answered 503. 64 worst-case MCP alert reports at once peaked at 217 MB against a 512Mi container -- and the liveness probe is four times more forgiving than readiness, so sustained overload sheds traffic instead of restarting the pod. Expose the port through a reverse proxy, ingress or service mesh that enforces a header-read and idle timeout. The default sidecar deployment binds 127.0.0.1, where only containers in the same pod can reach it.
Sidecar Binds 127.0.0.1 only, so only containers in the same pod can call it (the pod is the trust boundary); no Service port, no token, no egress needed. CI proves the port is closed on the pod IP.

Homebrew The formula installs the release wheel and wheels-only dependencies pinned by hash from the release's requirements.lock.

The directory plugin and a remote server

The Claude plugin directory accepts a remote MCP server from an organization that is not Verified, so kube-noob-skills could declare an http server whose URL and bearer token come from userConfig and point it at the user's own kube-noob serve. It does not, for now. What the documentation says, read 2026-11-12:

  • A sensitive value "masks input and stores the value in secure storage instead of settings.json", and ${user_config.KEY} is substituted into an MCP server's url and headers (plugins reference). The token would not be written into the plugin's files.
  • But a server whose URL option is unset is an error, not an absence: Claude Code reports Invalid MCP server config ... URL is unset or invalid on the plugin's Errors tab (troubleshooting). Chat ignores such a server and Cowork ignores one whose option has no default (platform support). Most people installing from the directory will never run kube-noob serve, so the default state of every install would be an error, and a skill would have to name kubenoob_* tools that exist only on some installs.
  • kube-noob serve on a laptop is a local process presented as a remote one. That is the thing the directory gates on Verified status, reached by a side door; a reviewer could fairly read it that way.

The CLI path covers the same commands with no credential at all. If it is ever shipped, the server is optional, the token is a sensitive option and the URL has no default; tests/test_plugin.py::test_bundle_names_no_credential_variables does not cover it (it scans plugin/kube-noob/server/), so a test for the directory plugin has to refuse any literal header value. That decision is the maintainer's.

Capability tiers

kube-noob reads by default and changes nothing. Everything else is a tier, off by default; every action in a tier needs a person's approval for exactly that action, valid for 15 minutes and usable once. kube-noob doctor prints each tier and what it needs.

G gate.enabled forward a tool call a person approved to an upstream MCP server nothing from kube-noob; the upstream keeps its own access
M llm.provider kube-noob ask, train bench and the eval judge call a model; no MCP tool and no other command does the key named in llm.apiKeyEnv (only *_API_KEY variables, so never the server's own KUBE_NOOB_HTTP_TOKEN), or $ANTHROPIC_API_KEY for provider: anthropic -- which is that provider's default and is sent nowhere else. An openai-compatible endpoint with no apiKeyEnv is called with no Authorization header. Endpoint error bodies are redacted before kube-noob quotes them. Refused under the offline lock unless the endpoint is loopback or *.svc
A admission.enforce (chart admission.enabled runs the webhook) kube-noob admission serve denies a create or update for a listed rule, and on an update only a finding the old object did not have; otherwise it only warns; it never mutates, and failurePolicy: Ignore means a dead webhook blocks nothing -- which KN-S030 reports as a HIGH finding, correctly: a policy gate whose purpose is to deny should set Fail. For this webhook the trade-off is deliberate and accepted on the record in .github/kube-noob-exceptions.yaml, because an audit webhook that is down must not stop a cluster admitting objects. If you audit your own kube-noob install you will see the same finding; accept it the same way rather than lowering the rule. The object's name is <release>-kube-noob-admission.<namespace>.kube-noob.io, so it embeds your release name and namespace, and a cluster-scoped exception must name it exactly -- copy the shape of our entry, not its name a serving certificate (OpenShift service CA, cert-manager or your Secret); with admission.lookups, a ClusterRole with get and list on PodDisruptionBudgets, NetworkPolicies, PersistentVolumeClaims, HorizontalPodAutoscalers and StorageClasses

Tier A is configuration rather than an action: whoever lists a rule in admission.enforce approves every denial of that rule, so it has no per-action approval. The read-only backends have no method that writes. Code that changes something exists only while its tier is on. kube-noob's own audit flags what the P and D Roles allow (KN-S017, medium): pods started by Jobs or added as ephemeral containers can act as any ServiceAccount in the namespace, so enable them only in namespaces that enforce Pod Security restricted.

Verdict receipts prove integrity, not authenticity

kube-noob audit --receipt PATH and kube-noob gate --receipt PATH write a document that binds every input by SHA-256, the tool version, the meaning of every rule, the settings that changed the verdict and the verdict itself, and kube-noob receipt verify PATH re-runs those inputs. It is not a signature and not an attestation:

  • there is no key, no signing and no cryptography dependency. Anyone who can run kube-noob can write a receipt for any input they hold, so a receipt says nothing about who produced it. The document states that in its own text (integrity.statement), the command says it on stderr when it writes one, and receipt verify repeats it with every answer. Do not treat a receipt as provenance, and do not accept one as evidence that a particular party ran a particular scan;
  • what it does prove is worth having on its own: that these exact input bytes, under these exact settings, with these exact rule meanings, give this exact verdict -- and that anybody holding the files can re-derive it offline. Check the inputs with sha256sum and the verdict with receipt verify;
  • receipt verify exits 5 and names what it could not get whenever it cannot reach that conclusion: a missing input, a digest that moved, a receipt from another kube-noob version, a rule set that has changed, a file added to a directory since, standard input, or a gate run that also read a Containerfile, a scanner report, a SARIF report, VEX, KEV or a rendered Helm chart. Exit 5 is not a pass, and a pipeline that treats it as one has no check at all. A payload that does not match the digest the document carries is refused (exit 4), not checked;
  • signing would be an adapter over this document rather than a change to it: the payload digest is the seam. No key handling exists in kube-noob today, and gh attestation and cosign below are how the released artefacts are verified.

Verifying releases

Both commands below need a network, and this section used to say nothing about that. gh attestation verify --repo asks GitHub's attestations API for the bundle; keyless cosign verify needs Sigstore's trust root (Fulcio and Rekor). kube-noob is offline-first, its airgap job proves the install and four workflows run with no interface and no route, and the operators it is built for are behind an air gap -- so the one instruction this file gives them could not be carried out where they are, and nothing here said so. That is the product's own rule turned on its own supply chain: a precondition that is absent, presented as though it holds.

On a machine with a network:

gh attestation verify dist/kube_noob-*.whl --repo kube-noob/kube-noob
cosign verify ghcr.io/kube-noob/kube-noob:<version> \
  --certificate-identity-regexp 'https://github.com/kube-noob/kube-noob/.github/workflows/release.yml@.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

Across an air gap, carry the material in and verify against it. gh attestation verify takes --bundle for "offline verification using attestations stored on disk", and cosign verify takes --offline with the bundle beside the image. Fetch both on a connected machine:

gh attestation download dist/kube_noob-*.whl --repo kube-noob/kube-noob
cosign download signature ghcr.io/kube-noob/kube-noob:<version> > cosign.sig

then carry the artefact and its bundle across and verify with --bundle. What is missing today, and is the reason this is written as a limitation rather than a recipe: the release publishes no bundle as an asset. Its assets are the wheel, the sdist, the chart, the krew archive, the skill zip, sbom.spdx.json and the demo GIFs -- measured on v0.10.0, where a query for any asset whose name contains bundle, sigstore, intoto or att returns zero. So an operator with no network has the artefact, the SBOM and no way to check either, and the offline commands above depend on someone having run the download on a connected machine first. Publishing the bundles as release assets is the fix and is owed; until it lands, the honest statement is that an air-gapped operator cannot verify a kube-noob release from the release alone, and the digests in sbom.spdx.json plus sha256sum are what they have.

Two things this does not say. The evidence receipts are a different claim and are unaffected: they are digest-bound and replayable, they are not signatures, and receipt verify needs no network (see above). And nothing here is a reason to skip verification where a network exists -- the commands work, they are the right ones, and the gap is the air-gapped case they never mentioned.

Those commands verify what was built after the project moved into the kube-noob organisation: the image for 0.9.0 and later, and the wheel for 0.9.1 and later. There is no 0.8.0 or 0.9.0 wheel: neither release reached PyPI (the 0.8.0 run failed before publishing and the 0.9.0 run failed at the PyPI step), so PyPI goes from 0.7.1 to 0.9.1. 0.7.1 and earlier were published from the previous account, and a signature cannot be moved: their images are at ghcr.io/aashishmahajan/kube-noob, their certificates name that repository, and gh attestation verify --repo kube-noob/kube-noob finds no attestation for their wheels. For one of those images:

cosign verify ghcr.io/aashishmahajan/kube-noob:<version> \
  --certificate-identity-regexp 'https://github.com/aashishmahajan/kube-noob/.github/workflows/release.yml@.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com

For one of those wheels, PyPI's own provenance names the publisher it was built by ("repository": "aashishmahajan/kube-noob"):

curl -fsS https://pypi.org/integrity/kube-noob/<version>/kube_noob-<version>-py3-none-any.whl/provenance
