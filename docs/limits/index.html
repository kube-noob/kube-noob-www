What kube-noob cannot tell you

Most security tools document what they find. This page documents what they miss, because a finding you trust for the wrong reason is worse than no finding. Everything here is a deliberate boundary, not a backlog item.

If you are evaluating kube-noob against another tool, read this page first and ask the other tool for its equivalent.

The one-sentence version

kube-noob reads manifests. It can tell you what you declared. It cannot tell you what your cluster runs, and those differ for reasons that have nothing to do with the quality of the analysis.

Four claims that are not the same thing

Treating these as interchangeable is the commonest way to over-read a clean report.

Claim What establishes it Does kube-noob establish it?
This is what the manifest declares Static analysis of the files Yes
The API server would accept this Submitting it to a real API server Partly — admission review evaluates offline, which is not the same as the server's answer
Admission actually enforces this The full admission chain, in your cluster, in order No
The workload behaves this way at runtime Observation of the running cluster No

A clean audit is evidence about the first row. It is not evidence about the fourth.

Rules that cannot be enforced at admission

kube-noob policy generate emits admission policies for about half the rules on Kubernetes and rather more on OpenShift, and lists the rest in the header of every generated file with the reason for each. The table below is generated by scripts/doc_numbers.py, so it moves when the rules do. How many depends on the platform, because several rules are OpenShift specific and generate there but have nothing to match on plain Kubernetes:

Platform Rules generated Not generated
kubernetes 47 46
openshift 4.20 54 39

Run kube-noob policy generate --platform <your platform> and read the header for the list that applies to you. The reasons fall into three honest categories:

  • The API server already refuses it. Generating a policy would duplicate a check the cluster performs anyway.
  • The rule needs objects admission cannot see. Admission evaluates one object. "No NetworkPolicy selects this workload" is a fact about a namespace, not about the object being admitted. kube-noob audit checks these over the whole bundle instead.
  • The rule belongs in CI, not at admission. A secret committed to Git is a property of the repository. Every Secret in a running cluster carries its data legitimately.

This is not a coverage gap being explained away. The rules on that list are ones an admission policy should not implement, and a tool that generated a policy for every rule would be producing policies that are wrong. (The two counts that used to be in this sentence are gone on purpose: they were hand-kept, they were platform-dependent, and one of them was still 78 when the code had 89 rules. The command's own header counts them for your platform.)

Network reachability: a policy verdict is not a packet

kube-noob policy reach evaluates AdminNetworkPolicy, NetworkPolicy and BaselineAdminNetworkPolicy in cluster precedence order and names the tier, policy and rule that decided. That is a statement about declared policy.

It is not a statement that a packet will or will not arrive. Three separate things must hold, and kube-noob can only speak to the first:

  1. Policy decision — what the declared policies permit. kube-noob answers this.
  2. Enforcement capability — whether the installed network plugin actually enforces those semantics. Kubernetes requires a supporting plugin for NetworkPolicy to do anything at all; installing policy objects on a cluster whose CNI ignores them restricts nothing. For the two admin tiers kube-noob now answers part of this when you name the CNI: --cni calico:3.32 reports every AdminNetworkPolicy and BaselineAdminNetworkPolicy in the input as not enforced (Calico removed support in 3.32 and stops applying them silently) and lets the NetworkPolicies decide, and a CNI whose support is undocumented makes the verdict undetermined. NetworkPolicy enforcement itself is still outside what kube-noob can see.
  3. Observed connectivity — whether a connection actually succeeded. That needs the running cluster.

Where kube-noob cannot see a policy that could change the answer — a ClusterNetworkPolicy, a Cilium or Calico cluster-scoped policy, a pod on the host network, an egress firewall outside the cluster — it returns UNDETERMINED and names what it could not read. It does not return allowed.

That matters more than it sounds. A checker that evaluates the NetworkPolicies it can see and stays quiet about the rest gives you a confident answer that is wrong in exactly the environments where cluster-wide guardrails exist. An allowed that silently ignored an unread policy is not a weaker answer than UNDETERMINED; it is a false one.

The same rule applies to malformed input: a policy document that cannot be parsed is not the same as a policy that does not exist. Skipping it would make the computed connectivity more permissive than reality.

The knowledge ceiling

Rules are checked against Kubernetes versions up to a recorded ceiling (CHECKED_THROUGH in src/kube_noob/catalog.py). Ask for a version beyond it and the report says so, in the output, rather than answering confidently for a version nobody verified.

An absent warning means the version was checked. It does not mean the cluster matches the manifest.

What is never read

kube-noob does not read Secret data, and no flag enables it. A rule about secret material therefore reasons about references — a literal value in an env var, a missing secretKeyRef — never about the value itself. A finding will name the field; it will not print the credential.

Out of scope entirely

Not gaps to be filled later. Different tools:

Not covered Use instead
Vulnerabilities inside image layers, SBOM extraction Trivy, Grype
Runtime syscalls, process execution, file integrity Falco, and the commercial runtime products
Cloud IAM, VPC and managed control-plane posture A CSPM
Helm's own error messages and template line numbers Nothing, currently — the broken line numbers originate in Helm's renderer, and a tool reading post-render output inherits them. kube-noob audits the rendered manifests and says so.
Whether a cluster is compliant with a framework A mapping is not an attestation. See below.

Compliance mappings are evidence, not conclusions

kube-noob maps findings to NIST SP 800-53 controls and names the matching RHACS policies. That is traceable technical evidence an assessor can follow to a control.

It is not a statement that your organization satisfies that control. Most controls have organizational and process components that no manifest contains. A tool that told you otherwise would be selling you a risk, not reducing one.

Why this page exists

The three-valued verdict, the documented 31, and the knowledge ceiling are the same design decision applied in three places: say what you do not know, in the output, where it cannot be missed. This page is that decision applied to the product as a whole.

If something on this page is wrong, that is a bug worth reporting.
