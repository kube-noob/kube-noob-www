0.9.2 - 2026-11-08

  • The chart installed an image that does not exist, and four other things the repository move broke (G266). kube-noob moved from a personal account into the kube-noob organisation. GitHub redirects the old repository URLs, so most references kept working and the breakage stayed invisible until each step ran. The ones that do not redirect: GHCR namespaces, the MCP registry namespace, cosign certificate identities, gh attestation --repo, and the site repositories.

Chart 0.9.1 is published and signed and defaults image.repository to the old namespace, while the release pushes to the new one -- so helm install with defaults ends in ImagePullBackOff. The Tekton Task, the GitLab template and the sidecar manifest hard-coded the same image. SECURITY.md told users to verify the supply chain with gh attestation verify --repo and a cosign identity that name a repository which no longer owns the attestations, so our own verification instructions could not succeed. CI could never have caught the chart defect: gate-ci built the image locally and tagged it with the old name before loading it into kind, so the test passed by minting the very thing it should have been checking for.

server.json and the mcp-name marker in README.md now both read io.github.kube-noob/kube-noob. That pair could only take effect in a new release: the registry reads the marker from the published PyPI description, and 0.9.1's is immutable, which is why publish-mcp-registry could not be fixed by a re-run.

Outside the repository and fixed by hand: the GHCR image and chart were private under the new organisation and are now public, and organisation policy had disabled deploy keys, which is what stopped the website publishing for twelve consecutive runs.

0.9.1 - 2026-11-07

  • 0.9.0 could not have published even with a green attestation (G265). The pinned PyPI publish action runs twine check dist/* and exec twine upload dist/* over the whole directory, and twine 7.0.0 rejects sbom.spdx.json ("Unknown distribution format") and the krew archive ("No PKG-INFO in archive"), aborting before it opens a connection. Both had been copied into dist/ since 2026-11-05, only so the GitHub release would attach them. v0.7.1 shipped before that change, v0.8.0 died on a missing PyYAML and v0.9.0 on a Rekor read-after-write 404 -- so publish-pypi had never once run with those files there. Reproduced with the action's exact twine before changing anything: check and upload both exit 1.

Two blind spots hid it. scripts/check_publishable.sh is the deliberate twin of the action's own check, down to the action SHA and the bundled twine, and it ran before the two steps that contaminated dist/. And ci.yml's publishable job builds the dists without ever running the SBOM or krew steps, so no pull request could see it: that sequence existed only in release.yml and was first executed on a tag.

Non-distribution assets now go to assets/, which github-release attaches and both attestation attempts cover -- krew's manifest points at that archive as a release asset, so it has to reach the release page. check_publishable.sh runs last, over the dist/ the action will actually see. Provenance is attempted twice with a pause, because v0.9.0 failed on Rekor returning 404 for an entry it had just written while every artefact was already correct; the retry still decides the job, so nothing public is ever unattested.

  • scripts/check.sh ran eleven fewer gates than it claimed (G264). It is what AGENTS.md tells you to run after any change to src/, and its header said it ran "every gate CI runs on code". It ran pytest -q where CI runs pytest --cov --cov-fail-under=80, so the coverage floor was never enforced locally, and it never built the wheel, installed and drove it, ran e2e_mcp_offline.py, check_publishable.sh, uv lock --check, either pip-audit, e2e_plugin.py, brew_formula.py --check, or the OSCAL schema validation and its did-it-skip guard. It passed four times running while CI failed.

All of those run now, and a tool this machine lacks is printed at the end under NOT RUN with the words "this is not a pass" instead of being passed over -- helm is the only entry here, because the chart guards have no helm-free path. tests/test_check_sh.py reads ci.yml and fails if a gate a code job runs is neither in check.sh nor named with a reason, which caught two holes in check.sh and one in its own first version. Running check.sh now takes about three times as long, which is the point.

0.9.0 - 2026-11-07

  • Two timing assertions measured the runner instead of the code (G263). test_a_padded_object_does_not_outrun_the_webhooks_timeout asserted elapsed < 5.0 for 4,000 containers; it measured 5.44 s on one shared 3.11 runner and held the 0.9.0 release, while 3.12, 3.13 and 3.14 passed the same code. The test is named for a shape and its docstring says the fix makes the cost linear, so it now times 1,000 and 4,000 back to back and asserts the growth stays under 8x -- quadratic in 4x the input is about 16x, linear about 4x, and a slow runner slows both halves alike. With G252's memo disabled the ratio is 15.7x and the assertion fires, so it still catches what the budget caught. A warm-up call comes first, because the cold call pays for imports. test_the_memory_demo_runs_offline_under_a_second had the same shape and keeps only a ceiling a hang would cross, with its real contract in the assertions on what the demo printed.

  • A corpus shard bigger than the bundle allows is written as parts. redhat-vex.jsonl is 2.78 GB, and db-bundle refuses a member over 300 MB, so the scheduled db image could not be built. The cap stays. A shard over 250 MB is <name>.jsonl, <name>-2.jsonl, and so on. A read concatenates them. A later write that fits in one file deletes the parts it no longer uses (G262).

  • The plugin and the wheel pin pydantic 2.14.2. 2.14.1 dropped JSON keys that matched an unused alias, and mishandled extra data on a TypedDict (GHSA-qpmf-fgh3-ff25, GHSA-3r8g-cqwr-jr29). The plugin lock moved and the skill install hint still said 2.14.1, so the bump could not merge. The hint, the plugin lock and requirements.lock now say 2.14.2.

  • policy reach against a live cluster no longer treats a Cilium or Calico cluster policy as absent. A pasted CiliumClusterwideNetworkPolicy or Calico GlobalNetworkPolicy was already undetermined. The live read never listed them, so the same objects on the cluster came back allowed and exit 0. Both are read once, cluster-scoped, from the published CRD (cilium.io/v2 ciliumclusterwidenetworkpolicies, crd.projectcalico.org/v1 globalnetworkpolicies). A 404 is "not installed". A 403 is not. The first read-only check is the get that lists that object. A namespace CiliumNetworkPolicy is still not read and still does not flip a pod-to-pod NetworkPolicy answer. The chart's cluster-scoped read role grants get and list for those two resources and nothing else new.

  • A cluster-scoped policy this tool does not read, and a hostNetwork direction, are no longer a false allow. CiliumClusterwideNetworkPolicy and Calico GlobalNetworkPolicy in the input join ClusterNetworkPolicy: the verdict is undetermined and the exit is 1, because either can reverse a namespace answer. An EgressFirewall, a namespace CiliumNetworkPolicy and a MultiNetworkPolicy stay on the "not evaluated" list and do not flip pod-to-pod traffic; they do not decide that traffic. A hostNetwork direction is unknown. It does not erase a deny that AdminNetworkPolicy or NetworkPolicy already returned, including a deny of that same pod. The summary says the NetworkPolicies would deny only when a direction they evaluated actually denied.

  • kube-noob gate -f on a Helm values file matches audit. A file named on the command line used to be audited anyway, so gate -f values.yaml reported KN-V001 (missing apiVersion). It now refuses with the same "nothing here is a Kubernetes manifest" error, exit 2. A directory walk still skips that file. A real manifest beside it still proceeds. A manifest-only gate still passes when Containerfile, vulnerability and code checks were not asked for.

  • helm template is given the Kubernetes version the caller already named. helm-audit and kube-noob gate --chart passed no --kube-version, so Helm 4.0.0 rendered .Capabilities.KubeVersion as v1.20.0. The flag is set only when --version was passed, and an OpenShift version uses the existing release map. No version still means no flag.

  • Install text matches the installer. Python is 3.11.4, and the skill runner in a checkout is skill/kube-noob/scripts/kn.py. The container example stays on the 0.7 tag the release publishes. The plugin instructions name Containerfile and SARIF tools only when that build still has them. The GitLab sample says why it cannot write when the job directory is not writable by uid 1001.

  • A peer kube-noob cannot check no longer lets a later rule allow the traffic. An AdminNetworkPolicy networks or nodes peer used to be skipped after a note, so a following Allow was allowed and exit 0. A CIDR is matched when the other side is an address, and 0.0.0.0/0 or ::/0 matches a pod whose IP is not in the manifests. Anything else that might match is undetermined. A priority above 99 is not evaluated: OVN-Kubernetes does not enforce it. A forbidden read of the admin tiers is not "the tier is not installed"; the namespace-scoped chart cannot read them, and that used to come back as a NetworkPolicy allow (G183).

  • A Jira run that cannot decrypt the previous main copy no longer starts a new one. The decrypt failure used to exit 0 and fetch from scratch, so the first green run after a passphrase mismatch became the artifact every later run restored, and the previous copy stopped being the main copy. The run now fails, the previous artifact is left where it is, and only fresh=true discards it on purpose. The upload also refuses a snapshot with fewer tickets than the copy it restored. The forward pass asks Jira ORDER BY updated DESC and, if the request budget runs out, resumes that same query from the page it had not applied, so a later run does not skip updates and does not write the same ticket twice (G182). The scheduled default is every other day (JIRA_EVERY_DAYS=1 for daily). Ticket text is still not published: it is queried locally with kube-noob ticket after corpus import.

  • The weekly corpus refresh has been refusing the copy since 2026-10-31, and the failure could not be acted on. The privacy audit exits 1 rather than keep Jira text with person-shaped content in it -- correct, and the reason it is a gate -- but it reported only 123 person-shaped findings: ['CNV-95960: spelled-out email', 'CNV-85843: account id', ...]. The ticket and the kind, nothing more, so separating a real leak from a false positive needed the encrypted copy and the passphrase, and the workflow stayed red for days. Printing the match would be strictly worse: that writes personal data into a public CI log. Each finding now carries the field it came from and a character-class shape of what matched, with no content kept: CNV-95960 text: spelled-out email A at A.A, CNV-85843 text: account id 9A9A9A9. Letters collapse to A and digits to 9, while at and dot survive because they are what makes a spelled-out email recognisable. docs/operations.md now lists the two known false-positive shapes -- a sha256: digest fragment matching BARE_ACCOUNT_ID, and a labelled commenter name before a hostname -- and says that anything else is a real leak to fix in the anonymiser rather than a reason to raise the gate. The patterns themselves are deliberately left broad: over-matching a digest costs a digest, under-matching costs someone's identity (G179).

It scanned text + " " + title, two fields that are sanitised separately, so a pattern could match across the join and refuse a copy over text present in neither -- "escalated to Commenter A at" and "example.com upgrade notes" are each clean and read as a spelled-out email when concatenated. Each field is scanned on its own, and the field is named in the finding (G180).

  • The weekly risk review opened an issue a week and never closed the previous one. risk-review.yml searched for an open issue titled with this week and edited it, else created one, and never touched the week before -- so 2026-W44 ("release recommended: no, no action needed this week") sat open from 27 October while W45 replaced it, and by December there would have been six open issues all reporting that nothing is wrong, with any week that did need attention among them. An open issue is a claim that something wants doing; a report that has been superseded is not making that claim. The step now closes every other open risk-review issue with a comment naming the week that replaced it. Two details that matter because this runs unattended: the new issue's number is taken from gh issue create's own output rather than a follow-up search, because GitHub's search index is eventually consistent and an empty result would have closed the issue just written; and the run fails loudly rather than closing anything if the number cannot be established. Both paths were exercised against a stubbed gh before shipping -- creating closes the two superseded issues and not the new one, updating closes only the older one. W44 was closed by hand this once (G176).

  • The KN-N008 deprecation change shipped with no test, so the claim it added was unprotected. The commit added the k8s-kep-5707 citation and rewrote the description to say the field is deprecated in Kubernetes 1.36, and touched no test -- the suite stayed green at exactly the count it had before, which is what a claim with nothing asserting it looks like. Any later edit of that rule could have dropped the citation and the sentence and nothing would have said so. There are now four assertions: the KEP is cited and every citation resolves, the description names KEP-5707 and 1.36 and says "deprecated", the remediation names somewhere to go (KEP-5707 offers no successor inside the Service API), and a Service with externalIPs is still reported while one without it is not -- because a rule whose text improved while its detection broke is worse than leaving the text alone. Verified by mutation: removing the citation from rules.py fails test_the_rule_cites_the_kep_that_removes_the_field, so the assertion is real and not incidentally true (G175).

  • KN-N008 knew Service.spec.externalIPs was dangerous but not that it is now going away. The rule already carried CVE-2020-8554 and the DenyServiceExternalIPs admission controller; it predates KEP-5707, which deprecates the field in Kubernetes 1.36 behind a kube-proxy feature gate AllowServiceExternalIPs, plans to switch that gate off by default about four releases later and to lock it off three releases after that, and offers no replacement inside the Service API -- pointing instead to a LoadBalancer Service with a cloud provider, an Ingress controller, or the Gateway API, which it recommends for new deployments. The rule now says so, which turns "this is risky" into "this is risky and it is leaving on a schedule" and changes how a team prioritises it.

Two things are deliberately not asserted. The tentative release numbers (1.40 and 1.43) are given as tentative, because the KEP marks them so. And the gate's default at 1.36 is left out entirely: the KEP contradicts itself about it, with the Summary saying default: false and Phase 1 saying default: true, so there is no version of that sentence this rule can state as fact.

No new rule, no count change: the check, its fixture, its CEL and its controls were already right. Only the citation list (now including KEP-5707) and the explanation moved.

  • New rule KN-S029: a host on a probe or lifecycle handler, and the Pod Security denial it causes. A host on an httpGet or tcpSocket handler makes the kubelet -- a trusted node component -- open a connection to that address on the pod's behalf, so anyone who can create a pod can have the kubelet reach somewhere the pod itself may not be allowed to, including node-local endpoints no NetworkPolicy sees. KEP-4940 adds this to the Pod Security baseline as the probeHost check, enabled by a namespace's pod-security.kubernetes.io/enforce-version: v1.34 or later.

Both sides of the deploy were blind to it. audit did not look at the field, so nothing caught it before admission; KN-S029 now checks all ten paths the KEP names -- the three probes' httpGet.host and tcpSocket.host and the postStart/preStop handlers -- for containers and initContainers alike. And policy explain had no entry for the check, so a real denial fell through to the generic branch, which echoes the denial back as its own "fix" and attributes no rule, while readOnlyNextSteps still offered kube-noob fix, which could do nothing for it. The denial now reports relatedRules: ["KN-S029"] and a fix that names the fields to delete.

The check name was verified against the KEP rather than written from memory: it is probeHost, one word, in a message of the form probeHost (container "liveness" uses probeHost 135.45.63.4). A plausible-looking invention -- "restricted probe hosts" was the first guess -- would have produced a regex matching nothing real, and a test written against the same invention would have passed. A test now pins the name to the KEP's (G174).

  • The one result that could not fit in any caller's context was the one an MCP caller had no way to shrink. policy generate -o FILE stopped inlining the rendered set, but PolicyGenerateIn has no output field and an MCP caller has no filesystem to write to, so that fix reached the audience that was not the problem. Measured on the bundled rule set for OpenShift, policy_generate returned 392,307 bytes of compact JSON, about 98,000 tokens, 94% of it one YAML string -- more than most callers can hold, for a tool that is meant to be called by a model. A result the caller cannot read is worse than one that says how to ask for less. (Every byte count here is compact JSON, separators=(',', ':'), on the 78-rule set as shipped; an earlier draft quoted 380,670, measured before KN-S029 added the 108th generated policy.)

There is now a 128 KiB limit on the inline YAML, chosen from the measurements rather than picked: every rule on every engine is 392,307 bytes and every rule on one engine is still 186,000-201,000, while ten rules on two engines is 79,217 and five on one engine is 19,670. The limit sits above the queries a caller can use and below the ones that overflow it. Over the limit the result is the counts, skipped, yamlOmitted: true, the byte count (yamlBytes: 369793) and a sentence naming the three ways out -- rules, a single engines entry, or the CLI's -o. That turns 392,307 bytes into 14,334 (about 98,000 tokens into 3,600, a 96.3% reduction) with nothing a caller reasoned over removed. A request already under the limit is byte-identical to before, and allow_large: true returns the whole set for a caller that knows its own budget.

It refuses rather than truncates, deliberately: half a policy set is not a policy set, and a caller that applied one would enforce some rules and silently drop the rest -- a quiet partial answer, which this project treats as a wrong one (G173).

  • The removed-API tables say where they stop, so "no removals" stops meaning "nobody looked". REMOVED_APIS was read from the Kubernetes deprecated-API migration guide at 1.37 and the guide lists no removals after v1.32, so for any target up to 1.37 an empty answer is complete. Past it, api_history returned removedInTarget: [] and validate produced no removed-API finding, and neither said that nobody had checked that minor -- a verdict earned by absence, the same shape as G163. It stops being hypothetical on 16 December 2026, when Kubernetes 1.38 is released, and already today for --version 4.25, which maps to 1.38. catalog.CHECKED_THROUGH now names the ceiling; api_history returns checkedThrough and beyondCheckedVersions and says so in its note; and a report whose target is past the ceiling carries a notCheckedBeyond block, printed above the findings in text so a short clean-looking report cannot be read as clean. A target at or below the ceiling is byte-identical to what it was, so nothing that was already complete changed shape (G171).

  • policy reach answered "allowed" on a cluster whose real policy it cannot read, and exited 0. ClusterNetworkPolicy (policy.networking.k8s.io/v1alpha2) is cluster-scoped and decided before any NetworkPolicy, and this evaluator does not read it. The kind was already named under notEvaluated and already attached a caveat to every proposed manifest -- but the verdict still read allowed and the CLI still returned 0, so a CI gate merged on an answer a Deny in that policy reverses. A note in a JSON list does not stop a pipeline. With such a policy in the input the verdict is now undetermined, undeterminedBy names it, the summary says which way the NetworkPolicies alone would have gone and that the unread policy can reverse it either way, and the exit code is 1. Deliberately not denied: nothing here knows what the unread policy says, so unknown is the honest answer -- the same third answer a same-priority AdminNetworkPolicy tie already gets. A run with no such policy is unchanged, verdict and exit code both.

This is not a future-API edge case. Calico 3.32 (13 May 2026) removed AdminNetworkPolicy and BaselineAdminNetworkPolicy enforcement outright in favour of ClusterNetworkPolicy, so on a current Calico cluster the policy that actually decides the traffic is the one kind this evaluator cannot read (G172).

  • The debug/anp.py docstring said v1alpha2 kept the same action semantics. It does not. Six differences are now written out where anyone extending the module will read them, each one a way the existing evaluator would misread a v1alpha2 document: Allow is renamed Accept, so ANP_ACTIONS rejects every valid Admin rule; Pass is legal in the Baseline tier, which BANP_ACTIONS forbids; ports is replaced by protocols, and because _port_matches reads an absent ports key as "every port", adding the kind to collect without rewriting the matcher would read a rule scoped to one port as a blanket rule and widen every verdict -- worse than not reading the kind at all; the Baseline tier is no longer a singleton named default; egress peers gain nodes, networks and domainNames, none evaluated; and the per-list cap fell from 100 to 25.

OCP_TO_K8S stopped at 4.22 and answered 4.23 through the "OCP 4.x tracks 1.(x+13)" extrapolation. The row is now explicit, and the test moved to 4.24 so the extrapolation branch stays covered instead of being shadowed. An earlier draft of this entry and of the commit message said the branch "is taking" those rebases, which overstates it; the row is behaviourally a no-op either way, since the +13 cadence answers 1.36 on its own.

  • The FedRAMP 20x KSI mapping now has a release and a retirement list recorded before it is built. FRMR.KSI.key-security-indicators.json is at release 25.11C (published 2025-12-01), 20x is at current_status: Phase 2 Pilot, the eleven families are intact, and seven indicators carry retired: true: KSI-CMT-05, KSI-MLA-03, KSI-MLA-04, KSI-MLA-06, KSI-SVC-03, KSI-TPR-01, KSI-TPR-02. Evidence offered against a withdrawn indicator is worse than no evidence, so docs/roadmap.md N3 and docs/compliance.md now say that the allowlist ships with the release string and excludes those seven. Documentation only; no code claims a KSI yet.

  • Compaction skipped the excepted findings, so it did nothing for the callers who need it most. compact_report hoisted the per-rule constants out of findings, but Toolkit.audit puts the findings an exceptions file accepted in a separate top-level excepted list, and that list was left untouched -- so every caller with an exceptions file, which is every CI caller, got a report with hoisted findings beside un-hoisted excepted ones, each still carrying its rule's title, severity, stage, category, remediation, citations, stackroxPolicies and controls inline at about 794 bytes apiece. expand_report round-tripped findings alone, so expanding such a report produced two finding lists of different shapes. Both lists are now hoisted against one shared ruleInfo map and both are restored by expand_report; the per-finding exception block is never hoisted. With one exception on examples/netpol-shop.yaml the result goes 39 025 -> 24 674 bytes and the round trip through Toolkit.audit is exact. The existing round-trip test could not have caught this: it called analyze(...).as_dict() directly and so never produced an excepted key at all (G169).

  • policy generate -o FILE reported a byte count that was wrong on Windows. The count was len(text.encode("utf-8")) while the file was written with write_text, which translates \n to \r\n on Windows -- so the file was larger than the number returned, and a caller checking the size would have seen a mismatch on one platform only. It now writes the encoded bytes directly (G170).

  • Filing an exception deleted the control it was filed against from the compliance record. Report.as_dict builds controlSummary from self.findings, and the exceptions filter in Toolkit.audit replaced that list with the surviving findings before calling it -- so a control whose only evidence was an excepted finding dropped out of the report entirely. On examples/netpol-shop.yaml, one well-formed exception against KN-N001 removed AC-4, SC-7 and SC-7(5) from controlSummary, leaving them indistinguishable from controls no rule had ever evaluated. That is backwards: an exception is an owned, reviewed, expiring decision about a control, and the one thing a compliance record must never do is make a signed-off control look unexamined. controls.summary now takes the excepted rule ids as well and counts them apart, so those controls stay named with findings: 0, excepted: 1 and the note says what that means. A run with no exceptions is byte-for-byte what it was (G168).

  • Two results were mostly copies of themselves, and an MCP result is spent out of the caller's context window. audit_manifests carried each rule's title, severity, stage, category, remediation, citations, stackroxPolicies and controls on every finding that rule produced: on examples/ that is 105 findings over 19 distinct rules, so each constant appeared about five times and 53.9% of the 118 631-byte result was duplicates (~29 700 tokens). audit --compact, and compact=true on the tool, now hoist those fields once into a ruleInfo map keyed by rule id -- 118 631 -> 54 694 bytes, 37.9% on a single file -- and audit.compact.expand_report is an exact inverse, asserted by a round-trip test, so this is a hoist and not a guess about which fields a caller does not need.
