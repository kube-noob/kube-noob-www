Operators

Which operators are installed, and are any of them reported broken?

Two questions, the same input: a directory of manifests, a must-gather, or -- when you turn cluster access on -- the cluster itself, read-only, from clusterserviceversions and subscriptions and nothing else.

The input

Three objects: one operator with its Subscription, and one ClusterServiceVersion whose Subscription is missing. Collect your own with oc get csv,sub,ip,og -A -o yaml > olm.yaml.

apiVersion: operators.coreos.com/v1alpha1
kind: ClusterServiceVersion
metadata:
  name: ptp-operator.v4.21.0
  namespace: openshift-ptp
spec:
  version: 4.21.0
status:
  phase: Succeeded
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: ptp-operator-subscription
  namespace: openshift-ptp
spec:
  channel: stable
  name: ptp-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
status:
  installedCSV: ptp-operator.v4.21.0
---
apiVersion: operators.coreos.com/v1alpha1
kind: ClusterServiceVersion
metadata:
  name: rhacs-operator.v4.6.0
  namespace: rhacs-operator
spec:
  version: 4.6.0
status:
  phase: Succeeded

What OLM installed

Package, version, catalog, channel, approval mode, the namespaces it serves and its phase. OLM copies a ClusterServiceVersion into every namespace an operator serves; the copies are folded into one operator, never counted as more installs.

not read: installplans (not-read, optional: it only adds detail) no InstallPlan in the input, so it was not read
not read: operatorgroups (not-read, optional: it only adds detail) no OperatorGroup in the input, so it was not read

The answer opens with a verdict, partial here, not with a count: an input it could not read is named, and an operator whose state it could not determine is reported as such -- never as zero operators. Operators installed without OLM (Helm charts, plain manifests, OLM v1 ClusterExtensions) are outside this inventory: it reads operators.coreos.com objects only. --require-complete exits 5 on anything but a complete answer.

What the release notes say about them

operators issues is a lookup in the bundled OpenShift release notes -- not a vulnerability scan, and not a gate. The notes key issues by release and text, not by operator or operator version, so the match runs through a table of the names the notes use for each package.

fix: A fix is listed for an OpenShift release. The release notes do not say whether it ships in the OpenShift payload or in the operator's own bundle, which OLM updates from its catalog on its own schedule, so whether this operator has it is not determined. fixReleaseVsCluster compares only the listed release with the cluster's version: at-or-before, after, or unknown when either has no update number.
method: A release-note lookup, not a vulnerability check: each operator's package is looked up in a table of the names the OpenShift release notes use for it, and the issues whose text uses them are listed -- 'named' for the product's name, 'mentioned' for a component name or an issue that also names another product or the platform. The notes key issues by OpenShift release and text, not by operator or operator version, so an issue that uses none of those names is not found, 'named' says the notes name it, not that it is affected, and whether an installed operator carries a fix is not determined.

Read the verdicts, not the count. named means the notes name that operator, not that your version is affected; no-alias means kube-noob has no entry saying what name the notes use for the package, which is not the same as no reported issue; and whether an installed operator already carries a fix is not determined, because the notes do not say whether a fix ships in the OpenShift payload or in the operator's own bundle.
