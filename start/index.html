Install it, then the first five minutes

kube-noob is a command-line tool and an MCP server. It calls no model, and by default it makes no network request at all: everything below runs on files you already have. Version 0.11.1, Apache-2.0, Python 3.11.4 or newer.

Install

Taken from the product's own install page at this build, not retyped here.

brew tap kube-noob/kube-noob https://github.com/kube-noob/kube-noob
brew trust --formula kube-noob/kube-noob/kube-noob
brew install kube-noob
kube-noob demo --list
kube-noob audit -f your-manifests/ --platform openshift --version 4.22
kube-noob insight 'paste anything'
kube-noob doctor
uv tool install kube-noob
pipx install kube-noob

Every method installs two commands: kube-noob and its short form noob. The install page has pip-in-a-virtualenv, the Helm chart, the Agent Skill for chat on claude.ai, and what to do when an older install shadows the new one.

1. Get the example files

The commands in the README name files under examples/. They ship inside the package; write them somewhere a command line can name:

$ kube-noob examples copy examples

It never replaces a file without --force, never writes through a symbolic link, and checks every target before it writes any, so running it twice is safe. kube-noob examples list prints the table below.

2. Paste an error and read the ten lines you act on

Read-only steps first. Anything that runs inside a container or changes the cluster comes last and is labelled as needing approval. --format json or --format yaml gives the whole structured answer to a program.

$ kube-noob diagnose -f examples/events-crashloop.txt --platform openshift --version 4.22
DBG-OOM · Container killed for exceeding memory (OOMKilled / exit 137) · confidence 1.0
  evidence: signal pod_reason OOMKilled; Reason: OOMKilled; Exit Code: 137
  likely cause: Memory limit lower than the working set (JVM/Node heaps sized for the host, not the container).
  other possible causes: 2 (--format yaml lists them)
  1. read-only first:
     oc describe pod orders-api-7c4b9d6f5-x2lqp -n shop
       why: Last State: Terminated, Reason: OOMKilled
     oc adm top pod orders-api-7c4b9d6f5-x2lqp -n shop --containers
     oc get events -A --field-selector reason=OOMKilling
  2. change, only after the evidence (needs approval):
     - Set limits from observed p99 usage plus headroom; keep requests ~= steady-state usage.
     - JVM: -XX:MaxRAMPercentage=75 (container-aware); Node.js: --max-old-space-size below the limit.
     (3 proposed changes in all: --format yaml lists every one)
  caught before deploy by: KN-C004, KN-C005 (kube-noob audit)
  docs: k8s-resources (kube-noob search)
also possible: DBG-CRASHLOOP Container keeps crashing (CrashLoopBackOff) (0.9); DBG-IMAGEPULL Image cannot be pulled (ImagePullBackOff / ErrImagePull) (0.3). Their steps: --format yaml

known issues: not determined: No reported issue in the OpenShift release notes matches this text closely. The index covers OpenShift 4.20, 4.21, 4.22 as of 2026-10-27.

exit code 137: killed with SIGKILL - OOMKilled or forced kill after grace period
signals: event_reason BackOff, pod_reason CrashLoopBackOff, pod_reason OOMKilled, component kubelet
context: ns=shop, pod=orders-api-7c4b9d6f5-x2lqp, name=orders-api-7c4b9d6f5-x2lqp

Run the read-only steps first (get, describe, logs, events). Commands that execute in a container or change the cluster are listed separately and require explicit approval. Here they are marked (needs approval).

3. The answer you should distrust, and why it tells you

An empty list is the most dangerous output a checker can produce. The reported-issue lookup holds the OpenShift release notes it has, and it says in every format whether your release is one of them, so "no match" and "not checked" are never the same answer.

Asked aboutCoverageWhat it says
--version 4.21.5determinedOpenShift 4.21 is in the index (4.20, 4.21, 4.22 as of 2026-10-27): issues that cannot affect 4.21.5 are left out, so no match means none of its reported issues matches.
--version 4.16.20not-determinedKnown issues NOT DETERMINED for OpenShift 4.16.20: the index holds the release notes of 4.20, 4.21, 4.22 as of 2026-10-27, and 4.16 is not one of them. No match here does not mean no reported issue. Read the OpenShift 4.16 release notes, or refresh the index (kube-noob corpus known-issues --online).

A release the index cannot answer for does not change an exit code: it changes the sentence. The same statement travels with diagnose, insight, the must-gather report and kube-noob gate, which lists the lookup under "Not run".

4. One command for "here, look at this"

kube-noob insight takes a paste -- events, logs, a YAML file, an Alertmanager payload, a question in words -- classifies what kind of input it is, and runs the commands that answer that kind. It is a table of shapes and keywords, not a reader: no model is involved, here or anywhere else in kube-noob, and nothing about your wording is understood. Given text it recognises nothing in, it lists what it does recognise and a bundled sample that works, rather than guessing.

What was pastedKinds it recognised Commands it ran
examples/events-crashloop.txtevent lines (Normal or Warning with a reason), pod status or describe outputdiagnose
A sentence naming no Kubernetes objecta question or symptom in wordsdiagnose, search

And it says what the paste did not give it. On the second row above, from the same answer: “Read-only first: every step listed here only reads; changes come from the playbook or rule with a person's approval. The text names no Kubernetes or OpenShift object, so no cluster steps are suggested: paste the error, events or logs from the cluster, or give the platform.”
