Blast radius

If this workload is compromised, what can it reach?

posture scan starts at what is exposed. posture reach starts at the other end: the one workload a scanner just flagged, or the one an incident is about. The answer is five legs -- exposure, token, RBAC, Secrets, node -- and each leg is reached, none, or not determined, with the object and field that prove it.

Run on two files, it determines little -- and says so

This is examples/insecure-deployment.yaml: one Deployment and one Service. 4 of the five legs come back not determined, because a set of files cannot show the RoleBindings, Services, Routes or Ingresses it leaves out.

This is the point of the command, not a shortcoming of it. A tool that answered "no RBAC reach" from these two files would be telling you something it cannot know.

Assert the files are everything, and the absences become answers

--whole-bundle says: these files are the whole bundle that applies to this workload. Now an absence is evidence, and 1 leg remains open. --require-complete exits 5 until the answer is complete, so a pipeline cannot read "not determined" as a pass.

$ kube-noob posture reach deployment/orders-api -n shop -f examples/ --whole-bundle
Deployment/shop/orders-api: if compromised, reaches no capability the input shows; not reached by any exposure in the input; 1 leg(s) not determined

  exposure  none            no Service, Route, Ingress, HTTPRoute, GRPCRoute or VirtualService read reaches it, and the pod is not on the node's network

What it does not do

From the answer itself, every time -- not from this page.

  • File input: a set of files cannot show the bindings, Services, Routes or Ingresses it leaves out, so 'none' is said only of what the pod spec decides and the answer is not complete. Pass --whole-bundle (whole_bundle) to assert the files are everything that applies to this workload.
  • NetworkPolicies on the entry edge are not applied: check a path with `kube-noob policy reach`.
  • Cloud IAM and admission-time mutation are not modelled.
  • Roles that are not in the input are reported in notRead; cluster-admin, admin, edit, view, system:auth-delegator and kube-system/extension-apiserver-authentication-reader stand in by their documented rules, and admin, edit and view aggregate rules the input may not carry.
  • Exposure is read from Services, OpenShift Routes, Ingresses, Gateway API HTTPRoutes and Istio VirtualServices; other routing objects in files are named in notRead, and a live scan does not list them.
  • One token per pod is followed: the automounted one, else a projected one, else a mounted token Secret; a token passed in an environment variable or by a CSI driver's tokenRequests is not followed.
  • hostPort is not a node escape: it opens the pod on the node's network, which is an exposure.
  • Only the escalation rights the Kubernetes RBAC good-practices page names are ranked. A short named list is known to grant nothing ranked (self and access reviews, token reviews, leases, events, status writes); any other bound resource and verb that is not a plain read is reported as not classified.

Reading a live cluster is opt-in and read-only (--cluster-enabled ... --live), and a list the cluster did not answer leaves its leg not determined -- a refusal and a 404 alike. Attack paths from the other direction are posture scan; see use cases.
