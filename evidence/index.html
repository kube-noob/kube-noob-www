Evidence

What does a reviewer actually open?

Not a console. One file, on a laptop, often with no network: an attachment on a change ticket, or the artefact a pipeline kept. So gate, posture report, posture diff and ksi all take --html and write a single self-contained page -- inline SVG, no script, no stylesheet, nothing fetched -- that prints to paper as it stands. The posture pages carry charts: findings by severity, open findings per control, the five standing buckets, and open against excepted over the snapshots kept.

It opens with the number no other scanner prints

This is the masthead of a real report, built from examples/insecure-deployment.yaml when this site was built. Above a numbered section 1, "Limits of this examination".

The gate failed.

15 findings at --fail-on high for platform openshift. 3 checks never ran because no input was given for them: that is not a pass, and section 1 says what they would have covered.

Every other scanner reports only what failed. A reader who sees only that number cannot tell a clean cluster from an unexamined one -- so what reached no verdict is a number of its own, beside the findings, not a column in a table thirty rows down. The ksi page counts indicators the same way, including how many have no kube-noob rule behind them at all.

$ kube-noob gate -f examples/insecure-deployment.yaml --platform openshift --version 4.22 --html report.html

An alert becomes a report before anyone opens a console

Point an Alertmanager webhook receiver at POST /v1/alert-reports on the in-cluster service and each notification becomes an evidence report per alert: the signals it carries, the playbook diagnosis, the reported OpenShift bugs for the release the alert's own openshift_version label names, fixes your team confirmed, and the read-only checks to run first. With alertReports.store the server keeps it and on-call reads it back by id. The same report comes from a payload file with no server at all.

$ kube-noob alerts report -f examples/alertmanager-etcd.json
Alert evidence report: 0 alert(s)
verdicts: 
version: not named by the payload
caveats:

Every section says what it could not determine -- no version label, a release outside the issues kube-noob carries, no playbook, no team memory repository -- and an alert it recognises nothing in says exactly that instead of looking healthy. The receiver configuration is on the operations page, with the Prometheus metrics, the alert rules and the Grafana dashboard the chart can install.

Formats something else already reads

SARIF 2.1.0

audit --format sarif and gate --sarif: findings in GitHub code scanning, with the NIST controls on the rules and the blind spots in the same file.

OSCAL 1.2.3

audit --oscal and gate --oscal write assessment-results, validated against NIST's own schema in the product's CI.

FedRAMP 20x KSI

kube-noob ksi projects one audit onto the key security indicators, and reports how many have no kube-noob evidence at all. The crosswalk.

Pull-request annotations

gate --github-annotations and the Action's annotations input put findings on the diff; nine per kind, and the tenth says how many are not shown.

Exceptions are a file, not a flag: an accepted risk carries an owner and an expiry (--exceptions), and the report lists what was excepted rather than hiding it.
